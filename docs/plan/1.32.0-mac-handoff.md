## 1. F3 check — is the deploy hook actually running today?

**Done 2026-09-28** — F3 settled by probe (the hooks' `cd` targets do not exist on the Mac) and the migration applied; see `docs/plan/deploy-action.md` § Amendments. The steps below stay only as the rollback reference.

**Step 0 — back up before the first launch of the new build:**
```
cp -R ~/.aki/devsync ~/.aki/devsync.backup-pre-1.32.0
[ -d ~/.aki/devsync-baselines ] && cp -R ~/.aki/devsync-baselines ~/.aki/devsync-baselines.backup-pre-1.32.0
```
Back up both directories: the migration deletes each pre-1.32.0 legacy baseline file from `~/.aki/devsync-baselines` once it moves that file's data into the new per-host `state/` layout (`sync::remove_legacy_flat_baseline`, called from `migrate_settings_and_state`), so that directory is not safe to skip even though it lives outside `~/.aki/devsync` itself. The very next action (building and running the new code) launches the new binary against the real data and triggers `migrate_settings_and_state_on_boot` (`lib.rs`'s `setup()`) — these backups are the only copy of the pre-migration state, take them before that launch, not after.

**Action:** on the Mac, build and run the current code (`npm run tauri dev`), then PUSH one of `api.akitao.com`, `aki-gegrok-bot`, or `akidevrule` (whichever is easiest to reach) and read the sync console output. This launch is the one that runs the settings/state migration and seeds `.akidevsync/project.json` for every reachable project — § 2 below rehearses the same migration against a copy of the backup taken in step 0, so its numbers describe what this launch is about to do, not something separate.

**Expected / decision:**
- Console shows `[WARN] post_push hook failed (ignored)` → confirms `docs/research/…-scope-2.md`'s F3 finding (the hook's `cd` target does not exist on the Mac, `run_hooks_on_remote: false` runs it locally). Proceed: run `node scripts/migrate-deploy-hooks.mjs` (dry run — prints exact before/after, writes nothing), read the diff, then quit the app and run `node scripts/migrate-deploy-hooks.mjs --apply` (backs up `projects.json` and the touched `project.json` files first; refuses and writes nothing if any of the three hooks' current text does not match `docs/plan/deploy-action.md`'s quoted text, if a project's `project.json` is corrupt/unavailable, or if the app (packaged `.app` or a `tauri dev` process) is still running).
- Console instead shows the deploy succeeding → **stop**, do not run the migration script. Re-check `execute_hook` (`sync.rs`) — this analysis missed something about how the hook actually runs.
- **Rollback for the real migration:** quit the app, then restore both backups:
  ```
  rm -rf ~/.aki/devsync && cp -R ~/.aki/devsync.backup-pre-1.32.0 ~/.aki/devsync
  [ -d ~/.aki/devsync-baselines.backup-pre-1.32.0 ] && rm -rf ~/.aki/devsync-baselines && cp -R ~/.aki/devsync-baselines.backup-pre-1.32.0 ~/.aki/devsync-baselines
  ```
  `project_config.rs` (the code that reads `.akidevsync/project.json`) does not exist at the `511cae9` (1.31.0) tag — confirmed via `git ls-tree -r 511cae9 --name-only | grep project_config` returning nothing — so a 1.31.0 relaunch after this rollback never reads the seeded `project.json` files; they sit harmlessly next to the project until a 1.32.0+ build reads them again.
- **Rollback for the deploy-hook migration specifically:** the script's own timestamped backups (`projects.json.bak-<ISO time>`, `.akidevsync/project.json.bak-<ISO time>` per touched project) — copy a backup back over the live file and relaunch to undo.

## 2. Migration rehearsal — on a copy of the backup, not the live data

**Action:**
```
./scripts/rehearse-settings-migration.sh ~/.aki/devsync.backup-pre-1.32.0 \
  --legacy-baselines ~/.aki/devsync-baselines.backup-pre-1.32.0
```
This rehearses from the step-0 backups — the previous state, per `release.B5` ("rehearse from the PREVIOUS state, never from empty") — never from the live, already-migrated `~/.aki/devsync`. Both paths are required arguments; neither has a default that could silently point at the live directories. The script copies each backup into a fresh temp directory (`cp -R`, read-only against the source) and runs the real `migrate_settings_and_state` (the same function `setup()` calls at boot) against the copy, via `sync_state.rs::tests::rehearse_migration_against_a_real_devsync_copy` (`#[ignore]`, gated on `AKI_REHEARSAL_DEVSYNC_COPY`, which the script sets). The script refuses to run against a source that already has a `state/` directory (already migrated) unless `--allow-migrated` is passed. Rehearsed here on Linux against a synthetic fixture only (see § Rehearsal verification below) — running it on the Mac against the real backup is the first run against the real project tree.

**What it prints and asserts, derived from the copy's own `projects.json` — never hard-coded:**
- Pre-migration: projects total, count per `remote_host` (`bien`/`akicloud`), count with an empty `remote_host`, and the number of legacy flat `baselines/<id>.json` files. **Expected: 30 projects total** (the owner's own count), split across `bien` and `akicloud`.
- A predicted `project.json` seed count: projects whose `local_path` exists as a directory, that do not already have a `.akidevsync/project.json`, and that have at least one non-empty legacy field (`name`, `production_url`, `pull_excludes`, `push_excludes`, `dev_cmd_override`, `build_cmd_override`) — mirroring `project_config.rs::is_all_empty` exactly (`pub(crate)`, read directly rather than reimplemented), since the actual seeding step runs from JS at boot and this Rust rehearsal cannot execute it directly (it can only predict what it will do).
- Post-migration: the test writes the migrated projects to the copy's `projects.json` and re-reads it from disk, then asserts the re-read count equals the pre-migration total — this proves the migration survives an actual disk round-trip, not just an in-memory `Vec` compared to itself.
- One `state/<id>/<host>/` dir with a `baseline.json` for every project that had a legacy baseline **and** resolved to a non-empty host — count matches the legacy-baseline count above. A project with a legacy baseline but an empty `remote_host` fails this assertion (there is no host to place it under) — if that happens, it names an existing project with no configured remote target, worth confirming by hand before shipping.
- A second migration run (reloading from the disk file the first run wrote, not the leftover in-memory value) reports `changed: false` and every `state/` file plus `projects.json` byte-identical to the first run's output — proves idempotency on real data, not just the synthetic unit-test fixtures.

**After § 1's real launch, check the predicted seed count against reality:**
```
node -e 'const fs=require("fs");const ps=JSON.parse(fs.readFileSync(process.env.HOME+"/.aki/devsync/projects.json","utf8"));console.log(ps.filter(p=>fs.existsSync(p.local_path+"/.akidevsync/project.json")).length)'
```
counts the `project.json` files that actually exist once § 1's launch has run. **Expected relation:** this count is greater than or equal to the rehearsal's predicted seed count — equal if no project already carried a hand-written `.akidevsync/project.json` before this launch, or larger by however many did.

**Rollback / postconditions for the real first launch:** see step 0 and § 1's rollback above — the backup this section rehearses from is the same one that lets § 1's rollback restore cleanly.

**Rehearsal verification (this run, on Linux):** ran the script against a synthetic fixture copy — **REHEARSAL PASSED**, `--allow-migrated` refusal and predicted-seed/legacy-baseline counts confirmed working.
