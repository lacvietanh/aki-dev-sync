## 0. What this release is, and what it deliberately is not

The audit produced 57 actionable findings. Shipping all of them is neither possible nor wise: about
a third are latent risks that have never bitten, and two of the loudest are already-declared,
already-reasoned deferrals. This plan sorts them by **one question only** — *can a user lose data,
see a wrong number, or be attacked outside the security posture the project has already published?*

Everything answering yes is Wave 1 and blocks the build. Everything else is Wave 2 (real bugs, no
destruction) or Wave 3 (deliberate debt).

Three findings the audit raised are **corrected or downgraded** here after independent re-reading of
the source — see §6. An audit is evidence, not a verdict.

### 0.1 Decision rule (BINDING on every agent implementing this plan)

This plan **decides**. Where a finding admits more than one reasonable fix, one is chosen here and a
single sentence records *why, from the user's state of mind at that exact moment*. An implementing
agent follows the choice. It does not re-open it, does not add a setting to cover both, and does not
hand the question back to the user. Four rules produce those decisions:

1. **Decide from the user's psychology at that moment, not from the code's symmetry.** Ask what the
   person actually needs while it is happening: are they afraid of losing files? impatient at a
   spinner that may already be dead? holding a phone in another room with no way to reach the Mac?
   doubting whether the number on screen is real? That answer picks the fix — not which option is
   tidier to implement.
2. **Block the mistake that cannot be undone; relax the one that can.** Deleting the wrong remote
   tree, overwriting a colleague's file, mirroring onto the wrong host — unrecoverable, so pay the
   friction there without apology. Re-typing a project name, re-pairing a phone, clicking a button
   twice — recoverable, so never spend friction there. This is the tiebreaker whenever "safe" and
   "unannoying" pull apart.
3. **When state is ambiguous, tell the truth about it.** "Loading" / "broken" / "never configured"
   must be distinguishable, because the user's next move differs in each. A clean screen hiding a
   dead poller is worse than an honest one. This **never** licenses a new row, banner or status bar
   — CLAUDE.md *UI Extreme Narrow* is absolute, so the truth rides an existing element: button
   colour, outline, tooltip, or an `position: absolute` badge overlay.
4. **Leave open only genuine taste.** A question belongs to the user only if it is personal
   preference, or cannot be derived from what the feature is *for*. Everything derivable from the
   feature's purpose is settled here. This plan leaves exactly one such question open (§4, transport
   security), and says so explicitly rather than by omission.

## 2. Wave 1 — blocks the build (11 items)

Criterion: data destruction, silently wrong numbers shown to the user, or an attack surface **outside**
the posture already declared in `CHANGELOG.md` 1.20.0's *Security note*.

### §2.1 — Empty `local_path` makes rsync operate on `/` · WS-1 + WS-2 · **S**

**Symptom.** Clearing the "Local Path (Absolute)" field and saving turns the next PUSH into
`rsync -avz [--delete] / host:remote/` — the entire filesystem root is uploaded. PULL is **worse**,
not safer: it mirrors the remote *into* `/`, and `delete_on_pull` defaults to `true` on a new project.

**Root cause.** No layer rejects the empty string. `saveConfig`
(`src/composables/useProjectConfig.js:164-196`) validates nothing but `production_url`;
`save_projects` (`src-tauri/src/projects.rs:146-152`) is a bare `fs::write` with no validation at all;
`validate_project` (`projects.rs:101-108`) only rejects `..`, control characters, and an empty
`remote_host`. `sync.rs:418` then does `format!("{}/", "".trim_end_matches('/'))` → `"/"`.

**Correction to the audit:** the claim that PULL is protected because `create_dir_all("")` errors is
**wrong** — `std::fs::create_dir_all` short-circuits on an empty path and returns `Ok(())`
(`sync.rs:438-441`). PULL is fully reachable.

**Fix.**
- WS-2: `validate_project` rejects empty `local_path` and empty `remote_path`, and additionally
  requires `local_path` to be absolute. Apply the same check at the other two `format!("{}/", …)`
  sites (`sync.rs:560`, `sync.rs:710`) by routing them through the same validated struct.
- WS-1: disable Save in `ProjectConfigModal.vue` while `local_path` is empty, so the Rust rejection
  is a backstop and not the user-facing error.

**Decision (rule 2).** Block at *save* time, not at *sync* time, and block hard rather than warning.
Someone clearing that field is mid-edit and expects the app to catch an obviously incomplete
project; the alternative — letting it save and refusing later — means the failure arrives at the
moment they have already committed to a destructive mirror. Re-filling a field is free;
`rsync --delete /` is not recoverable at all.

**DoD.** Unit test in `projects.rs` asserting `validate_project` returns `Err` for
`local_path: ""` and for a relative path; manual: clear the field → Save is disabled; force it via a
hand-edited `projects.json` → PUSH and PULL both fail with a named error before rsync spawns.

### §2.2 — Shell injection in `open_local_terminal` and the remote SSH terminal · WS-3 · **S**

**Symptom.** A project whose `local_path` is `/tmp/x"; curl … | sh; :"` executes arbitrary commands
in a new Terminal.app window when the user clicks "open in Terminal". `local_path` is free text
(`ProjectConfigModal.vue:20`), not picker-only.

**Root cause.** `system.rs:142` builds `format!("cd \"{}\"", local_path)` — inside shell double
quotes, `$`, backtick, `\` and `"` all keep their meaning. `applescript_escape` (`system.rs:37-39`)
escapes for the **AppleScript** layer only, which is the wrong layer: it delivers a literal `"` to
the shell. Neither `validate_project` nor the charset guard at `system.rs:28-37` (which covers only
`host` in `open_remote_subprocess`) is on this path. Same class at `system.rs:170-175`
(`ssh {} -t 'mkdir -p "{}" && cd "{}" ; exec bash'` — a `'` in `remote_path` breaks out of the outer
single-quoted argument) and at `resolve_remote_path` (`system.rs:405-408`, path interpolated into
`bash -c "echo …"`).

**Fix.** One POSIX single-quote escaper in `system.rs`, applied at **every** site that interpolates a
path into a shell string — copy the escaping the in-app terminal already gets right
(`usePtyTerminal.js:129-132`: `'` → `'\''`). Not a per-site patch: a shared helper at the single
funnel, so a future call site inherits it (`METHOD-flow-audit` C2 — stop adding guards around a
badly-shaped step).

**Constraint (NEVER BLOCK THE UI).** These are existing `#[tauri::command]`s that spawn subprocesses.
Re-check each touched command still satisfies `async fn` + `spawn_blocking`; do not "simplify" one
back to a plain `fn` while refactoring the escaping.

**DoD.** Rust unit tests for the escaper covering `'`, `"`, `$(…)`, backtick, backslash, space,
non-ASCII. Manual: a project at a directory literally named `it's $(id)` opens correctly in
Terminal.app and prints no `uid=`.

### §2.3 — AG cache destroys one record and shows the other's numbers · WS-5 · **M**

**Symptom.** A Google account signed into both the Antigravity IDE and the AG CLI on the same host
loses one of the two cached readings on **every** poll, and a slot pinned to `x@gmail.com:ide` then
renders the **CLI** session's quota under the IDE label. Wrong numbers, not just lost history.

**Root cause — verified directly.** The module stores entities keyed `host|email:sourceType` but
dedupes them by **email alone** on three paths:
- `agUsageCache.js:151-152` (`persistAgAccount`): for each account in `allAccounts`, deletes every
  same-host, same-email key that is not the current `canonicalKey`. With `allAccounts` containing
  both `{X, ide}` and `{X, desktop_cli}`, iteration 2 deletes the record iteration 1 just wrote.
- `agUsageCache.js:179-182` (`loadAgAccount`): the fallback loop matches on email only, so a miss on
  `X:ide` silently returns the `X:desktop_cli` record.
- `agUsageCache.js:203-221` (`listAgAccounts`): a **read** function that `delete`s store entries,
  deduping by email — so the dropdown can never show both source types for one email.

Reachability is confirmed at the producer: `scripts/get-antigravity-usage.js:605-621` merges only
`desktop`+`cli` into `desktop_cli`; an `ide` snapshot for the same email is pushed separately into
`finalSnapshots`, so `allAccounts` legitimately carries two entries with the same email.

**Fix.** Make the entity identity `(host, email, sourceType)` everywhere — this is a shape fix, not a
guard. Concretely: the stale-key sweep at `:151-152` narrows to "same host, same email, same
sourceType, different key" (i.e. legacy unsuffixed keys only); `loadAgAccount`'s email-only fallback
is removed or restricted to the case where the caller passed a bare email with no sourceType;
`listAgAccounts` keys `bestByEmail` on `email:sourceType` and **stops deleting** — a read path must
not mutate the store.

**Decision (rule 1 + rule 3).** When a pinned account's exact record is genuinely absent, the card
shows an **empty/unknown** state rather than falling back to a same-email record from another source
type. A person opens this panel for one reason — to find out how much quota is left — so a number
that is confidently wrong is strictly worse than a visible gap: the gap prompts a refresh, the wrong
number gets acted on. The fallback that produced this is removed, not made smarter.

**Constraint (Regression Guard — Multi-entity State, ABSOLUTE).** This is exactly the 1.9.3 bug
class. Name every helper by its true scope. Verify with **≥2 entities present**: two source types for
one email on one host, plus a second email, plus the same email on a second host — after a poll,
confirm all four records survive and each slot renders its own numbers.

**DoD.** Unit tests over the store shape for the four-record fixture above. CHANGELOG entry states
explicitly **what was preserved**, not only what was fixed.

### §2.4 — Terminal `alive` desync kills a live shell · WS-4 · **S**

**Symptom.** Shell exits → both screens show `alive=false` → the Mac clicks RESTART and gets a fresh
prompt → **the phone still believes the shell is dead**. The next key tapped on the phone does not
send a keystroke; it calls `restart()`, which kills the Mac's just-created shell (with everything
running inside it) and wipes the scrollback. Symmetric in the other direction.

**Root cause — verified directly.** There is no "the shell came back" event on the wire.
`pty_restart` (`pty.rs:315-324`) emits `reset` with empty data **before** `spawn_if_absent` runs, so
even a liveness field read at that moment would be stale. `ptyBridge.js:53-55` relays only
`{data, reset}` — `alive` is dropped. The receiver (`usePtyTerminal.js:166-171`) updates `alive` only
when `frame.alive !== undefined`. `alive` is otherwise set true only on the screen that issued the
command (`usePtyTerminal.js:73, 86`). It self-heals only via `hydrateScrollback` / `pushScrollback`,
which do carry `alive` (`pty.rs:409`, `ptyBridge.js:29-32`) — i.e. on a tab switch or reconnect.

**Fix.** Emit liveness with the reset, **after** the spawn: move `emit_reset` in `pty_restart` to
after `spawn_if_absent` (or emit a second `pty-spawn` event), include `alive` (read from
`session.is_some()`) in `PtyOutputPayload`, and have `ptyBridge.js` forward that field. The generation
counter already prevents the old reader from clobbering the new session — do not weaken it.

**DoD.** Two screens open; `exit` on the Mac; RESTART on the Mac; type on the phone → the character
appears, the shell is not killed, scrollback survives. Reverse the roles and repeat.

### §2.5 — SSH failure is indistinguishable from "remote file missing" · WS-2 · **M**

**Symptom.** Three user-visible consequences from one defect:
- "Upload (select files)" with a dead SSH connection shows **no** overwrite-conflict dialog and
  pushes over live remote files — the exact scenario that dialog exists to prevent (`useSync.js:318-322`
  is dead code for this case; it only catches IPC-layer errors).
- `REPORT.html` is **auto-approved for deletion** (`useSync.js:118-130`, `:135`) because a
  `remote_mtime` of `0` compares as older than `lastSync`.
- Against a macOS/BSD remote, *every* existing remote file reports as missing, so "open REPORT.html"
  silently opens the stale local copy (`system.rs:460`'s `remote_exists &&` guard never passes).

**Root cause — verified directly.** `get_file_conflict_info` (`git.rs:136-222`) wraps the ssh call in
`if let Ok(out) { if out.status.success() { … } }` with **no else on either branch**, never reads
stderr, and returns `Ok(results)` unconditionally at `:220`. Entries are pre-initialised at
`:146-167` with `remote_exists: false, remote_mtime: 0`. Separately, `git.rs:189` hardcodes GNU
`stat -c '%Y'`; on BSD it fails, `2>/dev/null` masks it, the remote emits `STAT  <file>`, the empty
mtime fails `parse::<i64>()` at `:206`, and the entry is skipped — with ssh still exiting 0.

**Fix.** Two independent halves, both in `git.rs`:
1. Propagate the failure: return `Err` (carrying stderr) on spawn failure **and** on non-zero exit,
   so the frontend's existing cancel-the-push branch becomes live code. Do not invent a third
   "unknown" state the callers would have to learn.
2. Portable mtime: `stat -c '%Y' "$f" 2>/dev/null || stat -f '%m' "$f" 2>/dev/null` — the GNU form
   first (the common case), BSD as fallback.

**Decision (rules 2 + 3).** On an SSH failure the push is **refused outright** — no "continue
anyway" escape hatch, and the Toast names the host and the SSH error rather than saying "could not
check". Someone who just hand-picked files to upload is, by definition, about to overwrite remote
work they care about; offering them a one-click bypass at the exact moment the app has no idea what
is on the other end trades an unrecoverable loss for a recoverable annoyance, which is backwards.
Re-clicking Upload once the link is back costs seconds.

**Regression risk.** Turning a swallowed failure into a real error changes behaviour for users on a
flaky link: "Upload (select files)" will now refuse instead of silently pushing. That is the point,
but the error text must say *why* (host unreachable vs. no conflicts) or it reads as a new bug.

**DoD.** Point a project at an unreachable host → "Upload (select files)" shows a named SSH error and
does **not** push; PUSH `--delete` no longer auto-approves `REPORT.html`. Against a macOS remote, a
newer remote `REPORT.html` is actually pulled.

### §2.6 — Pairing token wiped on every app restart and every Off · WS-6 · **S**

**Symptom.** Restarting the Mac app, or clicking Off, makes **every** paired phone forget its token
and require re-pairing — directly contradicting the shipped promise that a phone "reconnects silently
across app restarts … until revoked".

**Root cause (verified in the audit, accepted).** Close code `4001` means both "server is shutting
down / disabled" and "your token is invalid". `web_server.rs:90` (`enabled: AtomicBool::new(false)`,
not persisted) and `:494-505` send 4001 on the disabled path;
`useCompanionPairing.js:31-33` treats any 4001 as revocation and calls `clearDeviceToken()`.

**Fix.** Split the codes: keep `4001` for *token rejected* (client clears), add a distinct code for
*server disabled / shutting down* (client keeps its token and backs off). Nothing else about the
pairing lifecycle changes.

**Decision (rule 1).** On the ambiguous code the phone **keeps** its token and shows "waiting for
the Mac" rather than dropping to the pairing screen. The person holding the phone is usually in
another room; the Mac restarting is the *normal* case and they cannot walk over to read a new code.
Guessing "keep" is also the cheap error — a genuinely revoked token simply fails again on the next
attempt and clears then, whereas guessing "clear" strands them every single restart.

**DoD.** Pair a phone; restart the app → the phone reconnects with no code entry. Toggle Off then On
→ the phone reconnects. Revoke the token explicitly → the phone *does* clear it and asks for a code.

### §2.7 — Tailnet peer can claim the `host` role without a token · WS-6 · **S**

**Symptom.** With Tailscale HTTPS enabled, any peer on the tailnet can connect as `role=host` and
drive the app with no token at all.

**Root cause (verified in the audit, accepted).** The role guard tests `is_loopback()`
(`web_server.rs:486`), but `tailscale serve --bg http://127.0.0.1:PORT` (`:886`) makes every tailnet
connection *arrive from* loopback.

**Fix.** Stop inferring authority from the peer address. The host role must be proven by something
the proxy cannot forge — a process-local secret minted at startup and handed only to the Tauri
webview. This is outside the declared "paired device may call anything" posture: an *unpaired* peer
getting host authority was never accepted debt.

**Decision (rule 2).** Fix the authority check rather than warning the user off Tailscale HTTPS.
Someone who turned on tailnet HTTPS did it to be *safer*; a feature that quietly grants full control
to every peer as the price of enabling encryption is the kind of trap a user cannot detect, cannot
undo, and would never suspect. No setting, no opt-out — the loopback inference is simply wrong and
goes away.

**DoD.** With `tailscale serve` active, a second tailnet machine hitting `?role=host` with no token is
rejected; the Mac's own webview still connects.

### §2.9 — Preview failure downgrades the typed-name confirmation to one click · WS-1 · **S**

**Symptom.** When `get_sync_delete_preview` fails, the operation becomes *more* dangerous (nobody
knows what will be deleted) but the barrier becomes *weaker* — the typed-project-name dialog never
appears, only "continue anyway".

**Root cause.** On failure `deleteList` stays `[]` (`useSync.js:78`), so all three
`if (deleteList.length > 0)` blocks (`:106`, `:143`, `:155`) are skipped. The path is real even with
a live connection: rsync exit 23 (partial transfer) fails the preview while `--delete` still runs.

**Fix.** Invert it: `previewFailed` must **force** the typed-name dialog, with copy stating the list
could not be determined.

**Decision (rule 2).** Keep the operation available but make it the *hardest* barrier in the app,
rather than removing it. A failed preview does not mean the user is wrong to proceed — they may know
exactly what is on the remote — but they are now flying blind on a `--delete` mirror, so the
friction should be at its maximum precisely where the information is at its minimum. Typing a name
they already know costs five seconds; an unintended remote mirror costs the remote tree.

**DoD.** Break the preview (unreachable host, or a stubbed rejection) → the typed-name dialog appears
and a wrong name aborts.

### §2.10 — One dialog slot: a second confirm deadlocks the first project forever · WS-6 · **M**

**Symptom.** Mac asks to confirm PUSH `--delete` on project A; the phone starts PUSH `--delete` on
project B. A's dialog vanishes unanswered, its `await askConfirm` never settles, and
`projectRuntime[A].syncing` is stuck `true` **for the rest of the session** — project A can never be
synced again without restarting the app. Also a permanent leak in `_waiters`.

**Root cause.** `dialogStore.js:43-44` overwrites `pendingDialog` unconditionally; the per-project
guard at `useSync.js:45-48` only blocks the *same* project. Four call sites reach `askConfirm`
without a queue (`remoteActions.js:85`, `:228`, `:296`, and three in `useSync.js`).

**Fix.** Make `pendingDialog` a FIFO queue: `askConfirm` enqueues, `resolveDialog` pops and promotes
the next. The mirror already carries whatever `pendingDialog` holds, so the wire protocol does not
change shape — only the head of the queue is published.

**Decision (rule 1).** FIFO, and the queued dialog waits **silently** — no counter, no "1 more
pending" text. The user answering a delete-confirmation is concentrating on one irreversible
decision and reading a file list; telling them another question is stacked behind it splits exactly
the attention that dialog exists to capture. The second dialog simply appears when the first is
answered, which is what a person expects from a queue anyway. (Also the only option compatible with
*UI Extreme Narrow* — a badge would have to live somewhere new.) Last-in-wins was rejected outright:
it discards a decision the user already started making.

**Regression risk.** First-answer-wins across two screens (verified correct today, audit C7) must

### §2.11 — DRY silently makes "Upload (select files)" transfer nothing · WS-1 · **XS**

**Symptom.** The tooltip says the action is *"unaffected by the DRY toggle"*. With DRY on, the user
picks files, confirms an overwrite dialog, sees "Sync complete" — and **not one byte moved**.

**Root cause.** `startSync` sets `isDryRun = project.dry_run` (`useSync.js:51`) without consulting
`specificPaths`, and passes it through (`:207`) into the `specific_paths` branch of
`build_rsync_args` (`sync.rs:357-362`).

**Fix.** Make the code match the documented contract: force `isDryRun = false` when
`specificPaths.length > 0`. Cheaper and less surprising than rewriting the tooltip.

**DoD.** DRY on, select one file, confirm → the file is present on the remote and
`last_sync_action` reads `PUSH SPECIAL` without the `(Dry)` suffix.
