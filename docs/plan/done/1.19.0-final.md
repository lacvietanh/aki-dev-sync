# 1.19.0 final — narrow consistency, usage clarity, remote AG, statusline color truth

Status: in progress (2026-07-25). Base: `20de7cb` (Remote Control, 1.19.0).

Follow-on batch after Remote Control. Seven items, split across four parallel workstreams by
**exclusive file ownership** — the same mechanism that made `docs/plan/done/narrow-mode-and-ux-1.14.0.md`
(the original 700px narrow pass) safe to parallelise. No two workstreams may write the same file.

## Shared contracts (all workstreams)

- **Narrow breakpoint is `700px`, one value, already established.** `@media (max-width: 700px)`, plus
  the global helpers `.u-narrow-hide` / `.u-wide-hide` in `src/assets/main.css`. Never introduce a
  second breakpoint. `ProjectConfigModal.vue`'s `560px` is a drift bug, not a precedent.
- **Extreme-narrow UI principle** (project `CLAUDE.md`): no new rows/banners/labels to convey state.
  Colour, outline, badge overlay, tooltip only.
- **Scoped `<style>` beats a global media query.** A rule that must win inside a component's scoped
  block has to be written inside that component (this exact trap is logged in
  `docs/plan/done/batch-jul21-ux-fixes.md` §0).
- **Rust:** any `#[tauri::command]` touching a subprocess/SSH/network is `async fn` + `spawn_blocking`.
- Compilation happens on the Mac only. Reason statically; do not run `cargo`/`npm run dev`/`build`.

## A. Narrow consistency for the modals that the 1.14.0 pass missed (WS-B)

The 700px pass covered the header, the table and the usage panel. The modals got only the shared
chrome trim (`.modal-overlay/.modal-header/.modal-body/.modal-footer` padding in `main.css`) — their
own internal layouts were never audited. At ~420px wide, forms, button rows, tables and chip lists
inside `GitModal`, `ProjectTasksModal`, `ProjectConfigModal`, `SshConfigModal`, `RefreshSettingsModal`,
`ChangelogModal`, `GlobalNoteModal`, `UpdateModal`, `ClaudeProfileModal`, `IntroModal` still overflow
or wrap badly.

Required:
1. Audit each modal at ~420px and at 700px. Fix overflow, horizontal scroll, cramped labels.
2. Delete the `560px` breakpoint in `ProjectConfigModal.vue` — fold its rules into the 700px one.
3. Reuse `.u-narrow-hide` for text that should collapse to icon-only; do not invent per-modal
   equivalents.
4. Any rule that applies to ≥3 modals goes in `main.css` once, not copied per modal.

## B. Usage display — a full 7d pool greys out its own 5h (WS-C)

When a pool's 7-day/weekly quota reads 100%, its 5-hour figure is noise: the pool is exhausted
regardless. Grey the 5h reading out (dim, no colour ladder) so the eye goes straight to the number
that matters.

- Scope is **per pool**, never global: AG has two pools (Gemini, Claude/GPT) each with its own 5H+7D
  `UsageCircle`; CC has one pool with a 5h and a 7d bar. A full Gemini 7d must not grey the Claude
  pool's 5h.
- Condition: 7d percentage `>= 100`. A null/N-A 7d greys nothing.
- Implement as a state passed down (e.g. a `muted` prop on `UsageCircle` + a class on the CC bar) —
  no new DOM rows, no banner. Tooltip may say why.

## D. Open DEV / BUILD / REPORT on the *focused* macOS Space — **CLOSED, not an app-side bug**

Symptom: Chrome/Terminal own a window on Space 5, the user is on Space 1, they hit REPORT / DEV /
BUILD, and macOS yanks them to Space 5.

**No code changed.** The plan's original assumption — "force a *new* window and it lands on the
focused Space" — is contradicted by Apple's own Mission Control documentation: a new document opens
on the Space where that app already has windows, not on the current one. What actually governs this
is a **user-side system setting**, not anything the app can call:

- System Settings → Desktop & Dock → Mission Control → *"When switching to an application, switch to
  a Space with open windows for the application"* (`NSGlobalDomain / AppleSpacesSwitchOnActivate`,
  default `true`).
- There is no public API to place another app's window on a chosen Space; the Window Server calls
  that can (yabai, Hammerspoon) are private and need SIP changes.

Why each candidate was rejected:

| Approach | Why it fails |
| :-- | :-- |
| `open -n <file>` | `-n` only bypasses Launch Services' singleton check. Chrome locks on its `user-data-dir`, so the second instance hands the request to the running one and exits — identical behaviour. On Safari it spawns a genuine second process with a messy shared profile. And the Space is still decided by the setting above. |
| `open -na "Google Chrome"` | Hardcodes the browser, destroying "default browser" semantics; same singleton problem. |
| `open -g` (background, no activate) | Does avoid the Space jump — but the window still appears on Space 5 and the user sees nothing at all. Trades an annoyance for a silent no-op. |
| AppleScript "create window, then activate" | `open_terminal_with_command` (`system.rs` ~56-84) **already does exactly this** (`do script` before `activate`). Nothing left to improve; the remaining jump is the setting, not the ordering. |
| `open -n` for Terminal | Spawns a second Terminal.app instance — directly breaks the cold-start double-window fix and makes `tell application "Terminal"` ambiguous between two processes. |

**Fix belongs on the user's Mac**, and is worth confirming before this is closed for good:

```bash
defaults write NSGlobalDomain AppleSpacesSwitchOnActivate -bool false && killall Dock
```

Then re-run the scenario from Space 1. Also check the Dock icon → Options → *Assign To* is **None**
for Terminal and the browser — an app pinned to "This Desktop" ignores the setting above.

**Adjacent finding, not fixed:** `snap_frontmost_terminal_window` (`system.rs` ~108-150) picks
`System Events → processes "Terminal" → windows[0]`. With windows spread across several Spaces, index
0 of the accessibility window list is not guaranteed to be the one just opened, so a snap can resize
the wrong window. Separate issue, unverifiable from Linux, left alone.

## E. `user-select: none` sweep, minimum classes (WS-B)

Today: `body { user-select: text }`, `button { user-select: none }`, `.top-header *`, plus seven
ad-hoc per-component declarations. Chrome text (labels, tabs, table headers, badges, tooltips) is
still selectable and gets highlighted by an accidental drag.

- Invert the default at the app-chrome level, not per component: make the app shell non-selectable
  and re-enable selection **only** where copying is the point — inputs/textareas, the console output,
  log/diff panes, paths and emails the user genuinely copies, and `[contenteditable]`.
- Target one global pair of rules in `main.css` (`.u-select-text` opt-in escape hatch), and remove
  the per-component duplicates that the global rule makes redundant.
- Keep it minimal: no new class per component. Selection loss on something copyable is a real
  regression — enumerate the copy-worthy surfaces before flipping the default.

## F. Statusline dynamic colour — one source of truth, real ANSI (WS-A)

Two defects, one root cause. The app paints the ladder with **Tailwind** hexes
(`TIER_HEX` in `ClaudeSettingModal.vue`: `#60a5fa/#34d399/#fbbf24/#fb923c/#f87171`) while the shell
script prints **ANSI** codes (`BOLD_BLUE=\033[01;34m`, `BOLD_GREEN=\033[01;32m`, …). They are
different colours at every one of the five tiers, so the swatch in the app never matched the terminal.
The same split exists for the eight-colour picker (`src/utils/statuslineColors.js` hexes vs
`ansi_for()` in `statusline.rs`).

1. **Bottom tier (<20%) → `\033[01;38;5;86m` (xterm 86, `#5FFFD7`).** The current bold blue is too
   dark to read on a dark terminal. Aquamarine stays visibly *colder* than the green tier above it,
   so the ladder still reads as a temperature ramp.
2. **One table, three consumers.** Each tier and each picker colour is written once as
   `{ key, ansi, hex }`, where `hex` is the **xterm-256 rendering of that exact ANSI code**, not a
   hand-picked Tailwind approximation. The Vue ladder, the Vue preview, and the generator all read it.
   `statusline.rs`'s `ansi_for()` and the script's `BOLD_*` block must agree with it — a mismatch here
   is the bug being fixed, so state explicitly in the code comment which file is the source.
3. **`title` shows the ANSI code** on every swatch in the dynamic-colour area (tier dots, ladder
   cells, the picker swatches) — e.g. `aqua — ANSI 01;38;5;86 (#5FFFD7)` — so a user can compare what
   the app draws against what the terminal prints.
4. `cargo test` (`npm run test:statusline`) covers the generator; it runs on the Mac.

## G. The two "Apply to" checkboxes (WS-A)

## Outcome (2026-07-25)

A, B, C, E, F, G implemented; D closed as a user-side macOS setting (see above). Four things worth
carrying forward beyond what the items asked for:

1. **The 700px block was dead code.** It sat above the base rules it overrides at equal specificity,
   so the cascade discarded it — the 1.14.0 modal chrome trim never applied once, and only
   `.u-narrow-hide` (which carries `!important`) ever worked. Moved to the end of `main.css` with a
   comment pinning it there. Everything else in item A was invisible until this was fixed.
2. **The colour drift was every tier, not just the blue one.** Confirmed and fixed at the root: one
   `{ key, ansi, hex }` table in `src/utils/statuslineColors.js`, mirrored (with comments naming the
   source) into `ansi_for()` and the script's `BOLD_*` block. Note the two sides had also mixed
   *palettes* — VGA hexes for some codes, xterm for others; the table is xterm throughout, and the
   bold-promotes-to-bright assumption is written down where it can be checked.
3. **Remote AG needed no Rust.** Only a fourth source + the shared tab loop. Its flag defaults
   **on**, like the other three. Polling follows `enabled` rather than display, so an upgrade does
   start one `ssh <host> node` probe per interval for anyone with a host selected — accepted
   deliberately: that is the same cost `ccRemote` has always carried, and an off-by-default would
   have bought a one-time SSH round trip at the price of two identical features diverging forever.
4. **Log Out is now withheld on a remote card.** `logout_antigravity*` act on this Mac; offering
   them beside a remote host's readings would sign out the wrong machine. Not in the brief; kept.

### Open, deliberately not done here

- **The AG account cache is keyed by email, not by host.** `aki-antigravity-usage-cache-v2` is one
  map, so local AG and remote AG write into it together and the account dropdown will list accounts
  from both machines mixed. The fix is host-scoped cache keys plus a migration — a design decision
  of its own, and exactly the multi-entity store the project's regression guard is about, so it
  should not be improvised inside a UI batch.
- **`snap_frontmost_terminal_window` picks `windows[0]`** of Terminal via System Events. With windows
  spread across Spaces, index 0 is not guaranteed to be the one just opened, so a snap can resize the
  wrong window. Surfaced while investigating D; unverifiable from Linux.

## Verification

Static only on Linux: `npm run typecheck` is not configured in this project, so the gate is careful
reading plus `npm run lint:scripts` where remote scripts change. Everything runtime — a real Apply, the
Space behaviour in D, remote AG against a live host, narrow-width look — is a **Mac checklist**, not a
claim this plan may make on its own.

Mac checklist after build:
1. `npm run test:statusline` — generator suite.
2. Open Statusline Customizer, Apply to both targets, compare the terminal's <20% colour against the
   app swatch and its `title`.
3. Resize the window to its narrowest preset, open every modal in turn.
4. Turn remote AG on with a host selected; confirm AG and CC both poll and that turning one off does
   not stop the other.
5. Fill a 7d pool (or fake the payload) and confirm only that pool's 5h greys.
6. From Space 1, with Chrome/Terminal open on another Space, hit REPORT / DEV / BUILD.
