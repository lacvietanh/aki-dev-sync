## 0. Goal, and what this release deliberately is not

**Goal.** Make the in-app terminal's limits honest and its panel cheap: a per-project cap the app can actually keep, a global ceiling and a byte budget that are derived from each other rather than set independently, a collapse that hides instead of destroys, and a relay that can talk to one remote browser without shouting at every connected remote browser.

**Non-goals — stated so nobody widens the diff mid-execution:**

- **No design-token sweep.** 696 colour literals and 191 font-size literals stay where they are. Reasons and the corrected framing: §6.1.
- **No component splits.** `ClaudeSettingModal.vue`, `AgentUsage.vue`, `ProjectTable.vue`, `AppHeader.vue` are not touched structurally. Reasons, including two verified hazards that make one of them actively unsafe to split right now: §6.2.
- **No new frame type on the wire.** §13 of `docs/plan/done/remote-control.md` stays frozen. W3 adds two *optional fields* to existing frames, and a frame without them behaves exactly as today.
- **No new DOM element anywhere.** Every user-facing change in this plan is a number, a string, a colour, or a `title` attribute on an element that already exists (CLAUDE.md, Extreme Narrow).
- **No change to what a shell is or where it lives.** One PTY per tab, on the Mac, surviving every mount/unmount question this plan asks. Nothing here can lose a session.

### 0.1 Decision rule (BINDING on every agent implementing this plan)

Where this plan states a **number**, the number came from arithmetic that is written out next to it. Do not "round it up a bit" or "make it a power of two while you're in there" — every one of the four constants in W1 is load-bearing against the other three through INVARIANT R (§2.2), and a unit test will fail if you break it. If you believe a number is wrong, change the arithmetic in the doc and in the test, in the same commit, with the new derivation shown.

## 2. W1 — a per-project cap of 5, and the three numbers that follow from it

### 2.1 What is true today

- `MAX_TABS = 8` is one **global** cap, written twice: `src/store/terminalTabsStore.js:22` and `src-tauri/src/pty.rs:42`, kept in sync by comment because the Rust and JS build graphs share no constant.
- It is checked in three places: the store's `addTerminalTab` (host only — on a companion `action()` replaces the body with an RPC stub), `useTerminalTabs.js:123`'s `capReached()` (the companion's only chance to say anything), and `pty.rs:451` (the backstop that returns an error string).
- `SCROLLBACK_CAP = 256 * 1024` (`pty.rs:45`) bounds each tab's ring buffer.
- `COMPANION_QUEUE_LIMIT_BYTES = 2 * 1024 * 1024` (`web_server.rs:117`) bounds one connected
  companion's pending outbound queue.
- The global group can never drop below one tab (`closeTerminalTab`'s floor guard).

### 2.2 The arithmetic — measured from the code, not assumed

**How a scrollback replay is actually encoded.** Traced end to end rather than guessed:

1. `pty.rs` stores scrollback as **raw bytes** and base64-encodes on read (module doc comment, "BINARY-SAFE TRANSPORT"). `pty_get_scrollback` returns `data` as base64 (STANDARD alphabet).
2. `ptyBridge.js`'s `pushAllScrollbacks()` puts that string into `{ t, tab_id, data, reset: true, cols, rows, alive }` and hands it to `bridge.js`'s `send()`, which does `JSON.stringify` → one WS **text** frame.
3. The base64 alphabet (`A–Z a–z 0–9 + / =`) contains **no character JSON escapes**, so the JSON string length equals the base64 length exactly. There is no second expansion — this is the fact the estimate turns on, and it is why the answer is 1.33× the raw bytes and not more.
4. `web_server.rs`'s `frame_bytes()` charges `Message::Text(s).len()`, i.e. the whole JSON text.

So, per full tab: `base64_len(n) = ceil(n/3) * 4`, plus a JSON envelope measured at ~90 bytes and **budgeted at 128** — the figure the code and its test both use, so the table below states 128 rather than the raw measurement.

| `SCROLLBACK_CAP` | base64 | + 128 envelope | × 16 tabs (one full replay) |
| :-- | --: | --: | --: |
| 256 KiB (today) | 349,528 | 349,656 | **5,594,496** (5.34 MiB) |
| **128 KiB (chosen)** | 174,764 | 174,892 | **2,798,272** (2.67 MiB) |
| 64 KiB | 87,384 | 87,512 | 1,400,192 (1.34 MiB) |

Against today's 2 MiB budget: `2,097,152 / 349,618 = 5.998`. **Six full tabs blow the budget; five fit at 83.4%.** At today's `MAX_TABS = 8` the replay is 1.33× the budget — so a full stack's rehydrate has *never* fitted.

**INVARIANT R** — write this into both files and assert it in a test. **Two parts, not one**, because two different things can go wrong to one outbox and a single inequality cannot express both. (The first draft of this plan had only R1 and sized it for one replay without saying what guaranteed the "one"; the review that followed found both the missing guarantee and the missing second case.)

```
R1   MAX_TABS × (base64_len(SCROLLBACK_CAP) + 128)  ≤  COMPANION_QUEUE_LIMIT_BYTES / 2
R2   2 × MAX_TABS × (base64_len(SCROLLBACK_CAP) + 128)  ≤  COMPANION_QUEUE_LIMIT_BYTES
```

With the numbers of §2.4 — one full replay is `16 × 174,892 = 2,798,272` bytes:

| | Left-hand side | Bound | |
| :-- | --: | --: | :-- |
| **R1** | 2,798,272 | 4,194,304 | ✅ 67% of the half-budget |
| **R2** | 5,596,544 | 8,388,608 | ✅ 67% of the whole budget |

**R1 — the recovery replay fits, with half the budget left for frames that may not be dropped.** The factor of 2 is not padding for its own sake: a rehydrate is the *recovery* path, and it can be queued alongside a pending `init` snapshot and a run of `delta`s, none of which may be dropped. A recovery that can itself trip the failure it is recovering from is a livelock, which is precisely the bug (§2.3).

**R1's left-hand side is ONE replay only because the relay addresses a CONNECTION** (§4.2). The frame that triggers a replay, `companion-connected`, is emitted per connection and answered with a full replay each, so an address matched per *device* multiplies that term by however many connections the joining device has open — two browser tabs on one phone, or a reload racing the old socket's cleanup:

| Connections on the joining device | Replay bytes into each of its outboxes | vs R1 (4,194,304) | vs budget (8,388,608) |
| --: | --: | :-- | :-- |
| 1 | 2,798,272 | ✅ | ✅ |
| 2 | 5,596,544 | ❌ broken | ✅ |
| 3 | 8,394,816 | ❌ | ❌ trips `coalesce()` → the §2.3 livelock, unfixed |

**R2 — the reachable double does not trip a coalesce at all.** Two replays really can sit in one outbox at once, by different routes, and R1 cannot see the second: (a) the addressed one this connection asked for, and (b) an *unaddressed* one from `ptyBridge.js`'s `scheduleResync()`, which heals a hole the host's own congested socket left in every companion's stream and so has no single addressee. Bounded against the whole budget rather than half of it, deliberately — unlike R1's case both of these are `pty_output` and losing them is recoverable, so the only property worth buying is "this common pair costs bandwidth and nothing else".

**What neither part claims.** The queue's worst case is not finite: a sustained firehose congests the host socket repeatedly and each cycle queues another broadcast replay ~250 ms later into a phone that has not drained. That needs no budget to survive — those frames are exactly what `coalesce()` exists to shed, after which the queue is empty and the next addressed replay is the R1 case again. **INVARIANT R bounds the recovery path, not the queue.** Do not "fix" the unbounded case by raising a constant.

### 2.3 What actually goes wrong today — a correction to the commissioning framing

The framing says a full stack's expansion "can exceed the 2MB companion queue budget and **disconnect the phone**". Traced through `Outbox::push_within_budget`, that is not what happens, and the real behaviour is worse rather than better:

Every replay frame is a `pty_output`, and `is_coalescible()` returns **true** for exactly that tag. So on overflow: `coalesce()` drops *all* queued `pty_output` frames → `bytes` falls to near zero → the second budget check passes → **`force_close` is never reached and the socket is never cut.** Instead `resync_pending` is set; the writer sends only whichever tabs queued *after* the collapse; on drain it re-issues `companion-connected`; the host answers with a full 8-tab replay; it collapses again.

**That is a replay livelock.** The early tabs' scrollback never arrives, the loop repeats indefinitely, and each round costs the Mac a full base64 encode of every tab. `CLOSE_TOO_FAR_BEHIND` (1013) can only fire if *non*-coalescible frames alone exceed the budget, which a scrollback replay cannot cause. If a real disconnect was observed, its cause is elsewhere and is not fixed by this plan — say so rather than assuming this closed it.

### 2.4 The four numbers, decided

| Constant | Today | New | Derivation |
| :-- | :-- | :-- | :-- |
| `MAX_TABS_PER_SCOPE` (JS only, new) | — | **5** | User decision, non-negotiable. |
| `MAX_TABS` (global, both files) | 8 | **16** | `1 + 3 × 5`: the one global tab that `closeTerminalTab` guarantees can never be closed, plus three project groups each at their full per-project cap. |
| `SCROLLBACK_CAP` (`pty.rs`) | 256 KiB | **128 KiB** | Halves the replay a joining phone must receive and parse: 5.34 MiB → 2.67 MiB. |
| `COMPANION_QUEUE_LIMIT_BYTES` (`web_server.rs`) | 2 MiB | **8 MiB** | INVARIANT R at 16 tabs: R1 `2,798,272 ≤ 4,194,304` ✅ (headroom 3.0×) and R2 `5,596,544 ≤ 8,388,608` ✅. |

**Does a global cap still exist alongside the per-scope cap? Yes, and it must stay in Rust.** The per-scope rule bounds nothing the backend cares about: scopes are unbounded in count (one per project; 17 real projects on this machine today), so 5 per scope × 17 scopes is 85 shells and 255 raw OS threads. `pty.rs` is scope-blind — it only ever sees flat `tab_id`s — and teaching it what a project is would break the "terminal v2 required zero Rust changes" premise that `docs/arch/terminal-stack.md` records. So the ceiling stays exactly where it is, as a resource guard, and the per-project cap is a pure frontend rule layered above it.

**Why 16 and not 10.** This plan's first draft said 10 (= two full scopes), on a thread-cost argument. The UX stage's S1 finding is right and 10 is wrong: the binding constraint is not thread count, it is that **a project group's *first* tab must never be refused.** At 10, one full project group (5) plus the mandatory global tab leaves 4 — so a user with two projects in terminals hits a ceiling that maps onto nothing in their model, on a `TERM` cell with no badge, for a reason living in a group the screen is not showing. That is the worst possible shape for a refusal. At 16 the same user has 5 first-taps in hand after two full groups. The cost of the correction is 48 raw OS threads instead of 30 and 2 MiB of resident ring buffer instead of 1.25 MiB — neither is a wall, and the UX doc's claim that threads-and-ring "was never the real constraint at that scale" is correct.

**Which dial moved, and why both.** The coordinator asked this explicitly. Both moved, because each fixes a different failure:

- **`SCROLLBACK_CAP` → 128 KiB fixes join *latency*.** 2.67 MiB instead of 5.34 MiB on the wire, on every companion join and every congestion resync, plus 16 fewer megabyte-scale `xterm.write()` calls on a phone. Raising the budget alone would make the slow join *not fail*; it would not make it fast.
- **`COMPANION_QUEUE_LIMIT_BYTES` → 8 MiB fixes the *livelock*.** It is what makes INVARIANT R hold. It was also the right number to move because it is the only one of the four that is **worst-case-only** memory: a queue sits near-empty except when a link is genuinely wedged, whereas the ring is resident for the app's whole life.
- **Not cutting the ring to 64 KiB** (which would let the budget stay at 4 MiB): that buys ~16 MiB of hypothetical worst-case RAM by halving what a newly-joined phone can scroll back to — the wrong trade, since serving the companion's rehydrate is the ring's whole job.

**The scrollback cut is not a user-visible reduction on the Mac.** `TerminalView.vue:290` creates each xterm with `scrollback: 5000`, client-side and per mounted tab, and W2 stops those buffers being thrown away on collapse. The Rust ring feeds only (a) a fresh mount, (b) a companion join, (c) a congestion rehydrate. 128 KiB is roughly 1,000 lines at 128 columns — above xterm's own default. What shrinks is the history a *newly joined phone* inherits, and only that.

**Accepted cost of the budget raise.** `web_server.rs:113`'s comment currently states the design intent as "four paired phones cannot cost more than ~8 MB between them". At 8 MiB that worst case becomes 32 MiB, reached only when all four links are simultaneously wedged, and `force_close` still bounds it absolutely. Rewrite the comment to state the new intent and this arithmetic — do not leave it saying 8 MB.

**W3 is load-bearing for R1, not independent of it.** Addressing the replay does not shrink *that* connection's replay; it removes the N× multiplication across every other connected screen on every join. That much was already true when W3 addressed a *device*. What was not true, and is the reason §4.2 now addresses a *connection*, is R1's left-hand side: `companion-connected` fires per connection and is answered with a full replay each, so a device-level address puts N replays in each of that device's own outboxes — 5,596,544 bytes at two browser tabs on one phone, past R1's half-budget, and 8,394,816 at three, past the whole budget. At that point `coalesce()` eats the replay, `resync_pending` re-issues `companion-connected`, and the §2.3 livelock the budget raise was supposed to remove is back. **The budget cannot be sized against "however many tabs the user left open"**, so the address had to become the unit that asked.

### 2.5 The two-cap sync guard — a comment is no longer enough

Today's comment-only mirroring was defensible when the two literals were **the same number**: a drift was visible to anyone reading either file. That property is gone. The new set is four constants, in two languages, that are deliberately *different* from each other and bound by an arithmetic relation. A comment cannot check arithmetic.

**Decision: add Rust unit tests. Do not build codegen or a shared JSON file.** The repo already has the precedent for exactly this — `src-tauri/src/statusline.rs:1061` holds a verbatim `JSON.stringify(defaultLocalConfig())` copied out of a `.vue` file as a test fixture, and `web_server.rs` already mirrors `FRAME_PTY_OUTPUT` and the three close codes from `protocol.js` by comment plus behavioural tests.

1. In `pty.rs`: `MAX_TABS` and `SCROLLBACK_CAP` become `pub(crate)`. A test **reads `src/store/terminalTabsStore.js` itself** via `include_str!` and asserts against the literals that file actually contains, with a failure message naming the file and the two numbers that disagree. *(This was originally specified as "a literal restated in the test body" and implemented that way. It does not work: Rust literals asserted against Rust literals in the same file fire only when the Rust side moves, and the Rust side is not the drift that happens — changing `MAX_TABS_PER_SCOPE` to 6 in the JS left all tests green. `statusline.rs`'s `VUE_DEFAULT_JSON` is the same half-link and should be moved to this shape whenever it is next touched.)*
2. In `web_server.rs`: tests asserting INVARIANT R1 and R2 arithmetically against `pty::MAX_TABS` and `pty::SCROLLBACK_CAP`. **These are the ones that earn their keep** — they are the only thing in the repo that can catch someone raising `MAX_TABS` without noticing they just re-broke the phone. A third test pins R1's "one replay per outbox" to `dispatch`'s addressing, so narrowing the address unit back to the device fails here rather than silently at two browser tabs.

The JS→Rust direction stays a comment. Rule of Three: two constants is not three, and the invariant that actually matters lives entirely inside Rust.

### 2.7 The change, item by item

1. **`src/store/terminalTabsStore.js`** — `MAX_TABS` 8 → **16**; add `export const MAX_TABS_PER_SCOPE = 5`. `addTerminalTab` already receives `projectId`, so its own check becomes scope-aware: count tabs whose scope matches, refuse at 5, then check the global length, refuse at 16. **Scope first, then global** — a user in a 1-tab project group who hits the global ceiling must be told about the *other* groups, not told their group is full.
2. **Three exported message constants replace `TAB_LIMIT_MESSAGE`.** All interpolate their constant; none hardcodes a digit:
   - per-project: `This project already has ${MAX_TABS_PER_SCOPE} terminal tabs. Close one to open another.`
   - global group (scope refusal): `The global group already has ${MAX_TABS_PER_SCOPE} terminal tabs. Close one to open another.`
   - global ceiling: `All ${MAX_TABS} terminal tabs are in use. Close one in any group first.`
   `"in any group"` survives **only** on the ceiling string, where it is the truth. `scopeTabLimitMessage(scope)` picks between the first two; the ceiling is used directly.
3. **`useTerminalTabs.js` — `capReached()` becomes scope-aware and returns *which* cap fired**, and `openScopeTerminal` captures `activeTerminalScope.value` at its top and restores it in the `if (capReached()) return` branch (UX S2). One local variable, zero DOM.
4. **`useTerminalTabs.js` — the pending-claim TTL expiry speaks** instead of clearing silently (UX M1b): `No terminal tab opened on the Mac. It may have reached a terminal limit.` Hedged because the refusal reason genuinely never crossed the wire. This is the backstop for the one-round-trip-stale-mirror race, not a substitute for item 3.
5. **`TerminalCell.vue` and `TerminalTabStrip.vue` — existing `title` computeds gain the count** (UX M2), and at the cap the `+` chip takes its existing muted treatment plus `cursor: not-allowed`. Dimmed, never hidden: a hidden `+` reads as a bug.
6. **`pty.rs`** — `MAX_TABS` 8 → **16**, `SCROLLBACK_CAP` 256 KiB → **128 KiB**, both `pub(crate)`; `EXIT_NOTICE` becomes `[process exited. Press any key to start a new shell]`; the module doc comment's "3 raw threads per LIVE tab, bounded by `MAX_TABS`" line gets the new ceiling and the new resident-memory figure; add the two constant-guard tests.
7. **`web_server.rs`** — `COMPANION_QUEUE_LIMIT_BYTES` 2 MiB → **8 MiB**, its comment rewritten with §2.2's arithmetic and the new four-phone figure; add the INVARIANT R test.

## 3. W2 — collapse hides the terminal stack, it does not destroy it

### 3.1 What is true today

`DockStack.vue:30-31` is `<slot v-if="collapsed" name="peek">` / `<slot v-else>`. Collapsing the terminal stack unmounts every `TerminalView`; expanding remounts all of them and re-hydrates each from the Rust ring. `docs/arch/terminal-stack.md`'s "Mount semantics" section documents this as accepted, and `TerminalStack.vue`'s header comment records it as a deliberate follow-up left undone because `DockStack.vue` belonged to a different work package.

### 3.2 The change

**`DockStack.vue`** gains one prop, `bodyPersist: { type: Boolean, default: false }`, in the same voice as the existing `collapseVariant` — one configuration point, chosen by the specialization. When it is false the render path is **byte-identical to today**. When true, the peek slot keeps its `v-if` and the default slot is wrapped:

> **Erratum (2026-08-12):** `collapseVariant` (the `'chevron' | 'close'` prop referenced above) was **removed** — its `'close'` value made the terminal panel's collapse control render as an `fa-xmark` "CLOSE", which read as destroy-the-shells rather than collapse (bad UX). The panel now uses the standard chevron (COLLAPSE/EXPAND). `bodyPersist` is unaffected and remains. See `docs/arch/terminal-stack.md` and commit `0fa1008`.

```
<div class="dock-stack-body" v-show="!collapsed"><slot></slot></div>
```

The wrapper is unavoidable: `v-show` sets `style.display` on a single element and cannot be applied to a `<slot>`, which renders a fragment.

**`src/assets/main.css`** gains `.dock-stack-body { display: flex; flex-direction: column; flex: 1 1 auto; min-height: 0; }`. This is not cosmetic. The wrapper inserts a new node into the flex chain `.dashboard-bottom → .dock-stack → .terminal-mount-wrap` that `TerminalView.vue:314-318` records a fit as depending on; without `min-height: 0` the terminal cannot shrink below its content height, which is the classic flex-overflow failure and would show up as a panel that grows and never shrinks.

**`TerminalStack.vue`** passes `body-persist`, and changes `:active="t.id === activeTabId"` → `:active="t.id === activeTabId && !collapsed"`.

That second line is the whole re-fit mechanism, and it is why **no change to `TerminalView.vue` is needed**. It already has, at lines 271-281, a `watch(() => props.active)` that calls `scheduleFit()` and `term.focus()`, written verbatim for the case "the container was never resized, only shown — the ResizeObserver will not fire for that." Collapse sets `active` false on every view; expand sets it true on the active one; the existing watcher fits. Structural, not dependent on whether `ResizeObserver` happens to fire across a `display:none` transition in this WebKit build.

### 3.3 What it costs — each claim checked against the code, not assumed

- **No bogus fit while hidden.** `doFit()` bails at `width < 40 || height < 24` (`TerminalView.vue:220-221`), and a `display:none` container measures 0. So a hidden view never applies a wrong size and, on the host, never issues a `pty_resize` that would re-wrap the live shell. **Already guarded — do not add a second guard** (design.A8).
- **`ownsPtySize` authority is untouched.** Only the host fits; a collapsed host stack simply stops fitting; on expand it issues exactly one `pty_resize`, the same as any window resize today.
- **`ResizeObserver` does not leak.** It is `.observe(mountEl)` at line 322 and `.disconnect()` in `onBeforeUnmount` at line 330. With `v-show` it keeps observing a hidden element — spec-legal, producing no callbacks or one 0×0 callback that `doFit` discards — and is still disconnected on a real unmount (tab close, app teardown).
- **`term.dispose()` moves from "every collapse" to "tab close only."** This is the real cost: up to 16 mounted xterms, each holding `scrollback: 5000`, retained while the panel is closed. It is precisely what `MAX_TABS` now bounds, and it is the reason §2.4's ceiling had to be derived rather than picked.
- **The LOG stack cannot regress.** `LogStack.vue` does not pass `bodyPersist`, so its render path is unchanged. This is why the change is a prop and not an unconditional edit to `DockStack.vue`.
- **User-visible upside** (UX doc, "Collapse: hide-not-unmount"): xterm scroll position survives a collapse instead of dropping you to the bottom, and a full-screen program (`vim`, a TUI) comes back painted instead of being reconstructed from a ring buffer that may have trimmed the escape sequences that built it.

## 4. W3 — the relay addresses one companion instead of shouting at all of them

### 4.1 Two verified bugs, not one

1. **A second phone resets the first phone's terminal.** `handle_host_socket` (`web_server.rs:851`) calls `broadcast_to_companions` on *every* host frame, and `ptyBridge.js` runs `pushAllScrollbacks()` on every `FRAME_COMPANION_CONNECTED`. So phone B joining sends `reset: true` frames to phone A, whose `usePtyTerminal.js:382` clears and resizes its xterm. Phone A's screen is wiped and rebuilt mid-use.
2. **`invoke_result` cross-talk — the more dangerous one.** `bridge.js:60`'s `nextRequestId` is a *per-page* counter starting at 1, and `bridge.js:325` correlates purely on `pending.get(frame.id)` with no check of `to` or of any page identity. Two companions each send `invoke` with `id: 1`; `hostInvoke.js` replies `{ t: 'invoke_result', id: 1, ok }`; the relay broadcasts it; **both** pages resolve their pending id 1. Page B receives page A's result for its own unrelated call. That is silent wrong data, not a timeout — worse than a failure, because nothing reports it.

   **Note the unit: the counter is per PAGE, not per phone.** Two browser tabs on one paired phone collide exactly the same way. This is what makes §4.2's identity choice a correctness question and not a tidiness one.

### 4.2 The routing change

**Two optional fields, no new frame tag** — `docs/plan/done/remote-control.md` §13's freeze holds, because a frame carrying neither field behaves exactly as it does today, and an older companion bundle ignores fields it does not know.

- **Inbound stamp.** `handle_companion_socket`'s forward path parses the text frame and inserts `"from": <conn_key>` before `forward_to_host`, overwriting unconditionally. The companion never supplies this and therefore cannot forge it.
- **Outbound address.** `broadcast_to_companions` becomes `dispatch(msg)`: if the frame carries `"to"`, enqueue only into the handle whose `conn_key` matches; otherwise broadcast unchanged. The `to` parse is hoisted out of the per-companion loop, so it costs one parse per frame rather than one per paired phone.
- **Relay-originated.** `notify_host_companion_connected` carries the `conn_key` as its `id`, since the frame is a per-connection event and is answered with one full replay each.

**This makes the relay look inside a frame in a second place.** `web_server.rs`'s module header currently declares `is_coalescible` as "THE ONE PLACE" — that note must be updated to say two, and to state why the widening is bounded: the relay reads `t` to know what is re-derivable and `to`/`from` to know where a frame belongs, and nothing else. It still never reads app content.

| Frame kind | Routing | Why |
| :-- | :-- | :-- |
| `pty_output` with `reset: true` (scrollback replay) | **Addressed** | Bug 1. Only the joining/resyncing companion asked for it. |
| `invoke_result` | **Addressed** | Bug 2. It is a reply to one id, on one companion's private counter. |
| `pty_output` live chunks | Broadcast | One shared PTY; every screen shows the same bytes. |
| `pty_exit`, `pty_resize` | Broadcast | Shared liveness and shared size. Addressing them would be the 1.20.0 §2.4 desync bug rebuilt. |
| `delta` (incl. `dialogStore.pendingDialog`) | Broadcast | Mirror state. A mirrored confirm dialog answerable from any screen is a designed property. |
| `init` | Broadcast — **deliberately not addressed in this version** | It is idempotent (same snapshot, per-screen keys already excluded by `PER_SCREEN_KEYS`), so a spurious one is waste, not damage. Addressing it is an optimization, not a fix, and does not belong in a patch release. |
| `ping` / `pong` | Broadcast | Liveness. |

**Call sites:**

- `ptyBridge.js` — `pushAllScrollbacks(to)` gains the parameter, passed from the `FRAME_COMPANION_CONNECTED` handler's `frame.id`, and from `scheduleResync()`. **The congestion path matters as much as the join path**: `handle_companion_socket` re-issues `companion-connected` for the *one* companion that drained, and today that rehydrate hits everyone.
- `hostInvoke.js` — echo `frame.from` back as `to` on all three `send({ t: FRAME_INVOKE_RESULT, … })` calls, including the not-allowed refusal path.
- `protocol.js` — document both fields where the frame tags are defined.

**Identity: `to` names a CONNECTION (`conn_key`, `c<conn_id>`), not the persistent device id.** This plan's first draft chose the device id and wrote off the two-tabs-on-one-phone case as "one duplicate replay … not worth the protocol surface". That was wrong on both halves, and the review that found it is why this section changed:

- **It is not a duplicate, it is wrong data.** The request counter that collides is per *page* (§4.1.2). Two tabs on one paired phone each resolve the other's `invoke_result`, on a device-level address exactly as on a broadcast. The bug this workstream exists to fix would have shipped still live at one-device range.
- **It is not one duplicate replay either — it is N, and N breaks the byte budget.** `notify_host_companion_connected` fires per *connection* but carried the *device* id, and `ptyBridge.js` answers each with a full replay, which `dispatch` then fanned to every handle on that device. At two tabs each outbox receives 5,596,544 bytes, past INVARIANT R1; at three, 8,394,816, past the whole 8 MiB budget — which trips `coalesce()`, drops the replay, sets `resync_pending`, re-issues `companion-connected` and queues three more: precisely the §2.3 livelock. A reload before the old socket's `remove(&conn_id)` runs produces the same two handles.
- **The cost is nil.** It is not a second identity concept added alongside the device id; it *replaces* the device id in the same two fields plus `companion-connected`'s `id`. All three are opaque strings the host echoes and never parses.
- **It is also the safer stamp.** A device id is a value the device itself knows; a `conn_key` is minted from the relay's own counter and never shown to any companion, so it cannot be guessed either. `stamp_from` still overwrites unconditionally — that property is what makes `from` trustworthy and must survive every future edit.

**Device-level fan-out is kept exactly where it is the intent**: `revoke_device` still matches on `CompanionHandle::device_id` to close every live connection of one revoked device. Per-connection addressing narrowed the wire address; it did not remove the grouping.

### 4.3 Acceptance criteria

- [x] No new value is added to `protocol.js`'s frame-tag list. `to` and `from` are documented as optional fields on existing frames.
- [x] `dispatch()` with no `to` reaches every companion — a unit test, because this is the backward-compatibility guarantee the whole "frozen protocol" claim rests on.
- [x] A unit test that an addressed frame reaches only that connection's outbox with two companions registered — **and a second one with both connections on the SAME device**, since that is the case a device-level address would have passed while still being broken.
- [x] A unit test that pins R1's "one replay per outbox" to the addressing code, and states the 2×/3× arithmetic a device-level address would have produced.
- [x] `hostInvoke.js` echoes `from` on **all** reply paths including the allowlist refusal — a refusal that goes to the wrong remote browser is the same bug wearing a different hat.
- [x] `pushAllScrollbacks` has no remaining caller that omits `to`.
- [x] `delta`, `init`, `pty_exit`, `pty_resize` and live `pty_output` carry no `to` — grep the diff and confirm the only two `to`-setting sites are the two named above.

## 6. Deferred, with reasons

### 6.1 W4 — the design-token layer: deferred whole

**Measured first** (`src/**/*.{vue,css}`, my own greps, which differ from the commissioning framing — report the measured numbers, not the framed ones):

| Claim in the brief | Measured |
| :-- | :-- |
| 532 colour literals | **696** — 333 hex + 363 `rgb()`/`rgba()` |
| 75 re-spell an existing token | **96 raw occurrences**, of which 12 are the `:root` definitions themselves → **84 genuine call-site re-spellings** |
| 196 untokenized font-sizes, ~4 real roles | **191**, across 15 distinct values; the top five (11/10/9/12/13 px) account for **160 of 191 = 84%** — so "roughly 4 real roles" is right |
| 32 literal `700px` each claiming to be a source of truth | **32 occurrences, but only 15 are code.** The other 17 are comments, and nearly every one already cites `main.css` as the SSoT. |

**The `700px` framing is wrong, and it is the reason this item cannot be scoped down to "just do the breakpoint".** The 15 code occurrences are all `@media (max-width: 700px)`. **CSS custom properties are not valid in a media-query condition** — `@media (max-width: var(--x))` does not work. So these are not 32 competing sources of truth; they are 15 call sites of one *documented* value (`main.css:1303` declares itself the SSoT and the rest cite it) that plain CSS provides no mechanism to share. Fixing it needs `@custom-media` via PostCSS or a Sass step — a build-toolchain change, not a token sweep, and not something to do in a patch release alongside a relay-protocol change.

**The colour and font-size sweeps are deferred on blast radius.** 696 colour edits across ~60 files is a whole-app visual diff in a repo whose verification is `cargo test` plus `npm run build` — neither of which can see a colour. A reviewer cannot check that diff *and* the terminal/relay diff in the same release, and this project's own history (`docs/research/audit-release-window-jul28.md` lists the hardcoded-hex sprawl as still open from **1.15.1**) shows the sweep has already been deferred once for the same reason. It should be its own version, with its own before/after screenshots.

**What the eventual sweep should do** (recorded here so the next attempt does not re-derive it): start with the **84 exact re-spellings of the 12 existing tokens** — that slice is mechanically verifiable (`grep -c` per literal must reach 0 outside `main.css:27-38`), needs no new token invented, and cannot change a rendered pixel by construction. Do not mint a token per raw value found (`RULE-ui-pattern` A4: snap to the nearest existing step; a cluster of 9/10/11px is drift around one intended size). Rule of Three applies — a colour appearing twice is not a token.

### 6.2 W5 — component splits: all four deferred, one of them emphatically

**`ClaudeSettingModal.vue` (1665 lines) must NOT be split in this version.** Both hazards named in the brief are real; I verified them:

- **It writes to every remote host on open.** `watch(() => props.show)` at line 643 runs `Object.assign(cfg, loadCfg())` and then `checkAndAutoInstall()` (line 657), which SSH-probes every configured host (`check_statusline_status`, `statusline.rs:428`, one OS thread per host) and then calls `apply_statusline_config` — **writing the Claude Code statusline to every host that has Claude Code but no statusline**, using `cfg` as the payload. Splitting the modal means splitting ownership of `cfg`, and any change to *when* `cfg` is loaded relative to *when* the auto-install fires changes what is written to every remote machine the user owns. That is an outward-facing, hard-to-reverse side effect (`RULE-agent-behavior` B3) sitting inside the refactor's blast radius.
- **A cross-language SSoT lives in its `<script setup>`.** `statusline.rs:1061` holds a **verbatim** `JSON.stringify(defaultLocalConfig())` as a test fixture; `COLOR_EDITABLE` (`statusline.rs:100`) and `DEPENDS` (`statusline.rs:112`) mirror further literals from the same block. Move `defaultLocalConfig()` into a new module and the Rust test keeps passing against a fixture that no longer corresponds to any live code path. **A refactor whose principal safety net cannot observe it is the wrong refactor to run.** Doing it safely means first giving that SSoT a home both languages can point at — which is its own piece of work, not a by-product of a file split.

**`AgentUsage.vue` (1511 actual, not 1484), `ProjectTable.vue` (1359, not 1389), `AppHeader.vue` (1266, not 1278)** — deferred. Line count is not a defect (`RULE-design-core` B1: split by responsibility, not by file size), none of the three was named in a bug this cycle, and splitting them in the same version as a relay-protocol change and a terminal-cap change produces one diff nobody can review. ## 7. Where the commissioning framing did not match the code

Stated plainly, per instruction, because framing is not evidence:

1. **"Exceeds the queue budget and disconnects the phone."** It does exceed the budget, but it cannot disconnect: replay frames are `pty_output`, which is exactly the coalescible kind, so `coalesce()` fires and `force_close` is never reached. The real failure is a **replay livelock** in which the early tabs' scrollback never arrives at all (§2.3). If a genuine disconnect was observed, its cause is not this and is not fixed here.
2. **"32 literal `700px` each claiming to be a source of truth."** 15 are code, 17 are comments, the comments mostly *cite* the SSoT rather than compete with it, and CSS gives no way to share a value into a media-query condition anyway (§6.1). The value is not un-tokenized by neglect; it is un-tokenizable by the current toolchain.

Minor: the four component line counts in the brief are each off by 12-40 lines from the current tree (§6.2 lists the measured figures). Immaterial to the decision, noted so the numbers in the plan are the ones a reviewer will actually see.
