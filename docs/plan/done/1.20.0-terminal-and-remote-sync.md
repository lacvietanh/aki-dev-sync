## 0. Why these four items are one release

Three of the four are the same defect wearing different clothes, and the fourth is the feature that was already designed to sit on top of them. Every symptom the user reported traces to one of two shapes:

| Reported symptom | Real shape |
| :-- | :-- |
| Task note edited on the phone reverts after a while | A mutation reached **disk** without reaching the **Mac's reactive state** — the next full mirror broadcast replays the Mac's stale copy over it |
| Confirm-delete appears on the Mac, phone sees nothing | A **decision** is not representable in the wire protocol at all — designed in `remote-control.md` §3.4, never built |
| "Many flows still not really synced" | The two above, plus usage numbers living outside `src/store/*` so the mirror's glob never sees them |
| AG monitor on a remote host never updates, shows this Mac's numbers | Unrelated: a PATH-resolution failure over SSH, plus a cache lookup keyed too loosely |

So: fix the ownership shape first (§2), make decisions mirrorable (§3), then the terminal (§4) rides on a protocol that is finally trustworthy. The AG fix (§5) is independent and runs in parallel.

## 2. PERSIST-1 — a companion must never write the projects array

### The bug, exactly

1. The phone edits `tasksProject.value.notes`; that mutates only the **companion's own** mirrored copy of `projects` (`src/services/mirror.js:126`).
2. `saveProjectsList()` (`src/composables/useProjectConfig.js:127-133`) fires. It is a **bare** `invoke("save_projects", { projects: projects.value })` — the one mutating persistence path in the app that is not wrapped in `action()`.
3. On a companion, `invoke` is the seam-N RPC, so the frame carries the **phone's** whole array.
4. `src/services/hostInvoke.js:23-37` answers any invoke frame unconditionally and runs the real command; `src-tauri/src/projects.rs:145-152` is a pure `fs::write` — it never touches the host's reactive `projects` ref.
5. The Mac's in-memory `projects.value` therefore still holds the **pre-edit** note.
6. The next `broadcastFull()` (`mirror.js:102-109`, fired at `:150-152` when the host's own socket re-opens, or at `:160-162` on every `companion-connected` — i.e. **every time the phone reconnects after a screen lock, a backgrounded tab, or a LAN blip**) reads the host's own `STATE` and pushes the stale array back down, silently overwriting the edit.

That step 6 is the "chu kỳ reload" the user perceived. It is **phone-specific**: on the Mac the click handler already mutated `projects.value` in place before the invoke, so the host never needs the round-trip to be current.

### The invariant

> **PERSIST-1 — every mutation of a mirrored store ref happens on the host, inside an `action()`. A companion never ships a whole collection; it ships an id plus the smallest patch.**
> Corollary: `saveProjectsList()` is a **host-side persist of the host's own state**. It must only ever be reached from code already running on the host (i.e. from inside an `action()` body). Calling it from a companion-reachable path is the bug, and no guard inside it can fix that — by the time it runs, the wrong array is already in hand.

This is a shape fix, not a guard (`METHOD-flow-audit` C2: "just add another guard" is the red flag). We are not adding a command allowlist to `hostInvoke.js` — that would police the symptom while leaving the ownership rule unstated. The allowlist question is recorded in §7 as a separate decision.

### Work

New `action()`s in `src/store/remoteActions.js`, id-based, each touching exactly **one** project (`CLAUDE.md` multi-entity regression guard — verify with ≥2 projects present that the others are untouched):

```js
export const applyTaskEdit = action('remoteActions.applyTaskEdit', (projectId, patch) => {
  const p = byId(projectId); if (!p) return
  if (patch.tasks !== undefined) p.tasks = patch.tasks
  if (patch.notes !== undefined) p.notes = patch.notes
  return saveProjectsList()
})

export const reorderProjects = action('remoteActions.reorderProjects', (orderedIds) => { … })
```

Call sites to convert:

| Site | Today | After |
| :-- | :-- | :-- |
| `ProjectTasksModal.vue:176-181` `handleNotesChange` | `saveProjectsList()` | `applyTaskEdit(id, { notes })` |
| `ProjectTasksModal.vue:183-188` `handleDetailChange` | `saveProjectsList()` | `applyTaskEdit(id, { tasks })` |
| `ProjectTasksModal.vue:104` `@change="saveProjectsList"` | direct | `applyTaskEdit(id, { tasks })` |
| `useProjectTasks.js:85` `addTask` | `saveProjectsList()` | `applyTaskEdit(project.id, { tasks })` |
| `useProjectTasks.js:95` `toggleTaskProp` | `saveProjectsList()` | `applyTaskEdit(project.id, { tasks })` |
| `useProjectTasks.js:103` `removeTask` | `saveProjectsList()` | `applyTaskEdit(project.id, { tasks })` |
| `ProjectTable.vue:407` `onRowDragEnd` (drag reorder) | `saveProjectsList()` | `reorderProjects(ids)` |

`toggleTaskProp(task, prop)` takes a bare task with no project reference — give it the owning project (or its id) at the call site rather than searching for it; the caller in `ProjectTasksModal.vue` already has `tasksProject`.

Local optimistic mutation before the action is fine and wanted (the phone should feel instant): the action's own host-side write mirrors back and reconciles. What must never happen is the *persist* running off the companion's array.

**Leave alone** (already correct — they run inside actions, on the host): `useSync.js:207,240`, `useProjectConfig.js:95`, `remoteActions.js:58,114,129,205`.

## 3. Dialogs as mirrored state — implement `remote-control.md` §3.4

`grep -rn "dialogStore\|pendingDialog\|resolveDialog" src` returns **zero hits**: §3.4 was designed and never built. Every `Swal.fire()` is still a plain host-local `await`, invisible to the protocol, which is exactly why a phone-triggered PUSH `--delete` shows a spinner on the phone that never resolves while the Mac holds a modal nobody is standing in front of.

Per SYNC-1 a dialog awaiting a decision is a **data event**: both screens see it, whichever answers first wins. It rides the two existing seams — a mirrored ref plus an action. **No new frame type, no relay change.**

```js
// src/store/dialogStore.js  (auto-discovered by mirror.js's glob — zero mirror-side changes)
export const pendingDialog = ref(null)   // { id, kind, title, html, files, needsTyped, confirmText }
export const resolveDialog = action('dialogStore.resolveDialog', (id, answer) => { … })
```

Plus a promise-returning helper `askConfirm(spec)` (host-side only — it sets `pendingDialog` and awaits a promise keyed by `id`) and one `<DialogHost>` component mounted in `App.vue` that renders `pendingDialog` on **both** screens.

Four decision dialogs convert:

| Site | Dialog |
| :-- | :-- |
| `useSync.js:151` | type-the-project-name `--delete` confirm — **the reported symptom** |
| `useSync.js:81` | "preview failed, proceed anyway?" |
| `useProjectConfig.js:231` | `confirmRemove` — Remove Project? |
| `remoteActions.js:181` | SSH host missing → pick a replacement (an `input: 'select'`, so `DialogHost` needs a select kind, not just confirm/typed) |

Explicitly **out of scope**, and they stay `Swal.fire`:
* `useSync.js:323` — the overwrite confirm inside `openSelectDialog()`, which is bound to the native macOS file picker and is host-only by design (F3).
* `AgentUsage.vue:394` — the Antigravity logout confirm. It runs in the clicking screen's own component handler, never through an action, so it already appears where it was triggered.
* Every toast / success / error `Swal` — fire-and-forget UI, not a data event.

Correctness details that already have answers in §3.4 and must not be re-litigated:
* **First-answer-wins** via the `id` guard; the losing screen's click is a silent no-op.
* **The typed confirmation travels with the answer** and is validated **on the Mac** — the phone never gets to skip the safety check. Keep `preConfirm`-equivalent validation host-side.
* A dialog left pending when the host restarts is simply gone; the action awaiting it was lost with the process. No persistence.

`DialogHost` may render via `Swal.fire` under the hood, driven by the mirrored ref, to keep the visual diff at zero — the requirement is that the *state* is mirrored, not that the widget is hand-built.

## 4. In-app terminal (xterm.js + portable-pty)

Fleshes out `docs/arch/remote-views-roadmap.md` § Terminal View. It does not diverge from it.

### 4.1 The goal, restated

The ask is "xterm.js like VS Code". The **goal behind it** is: *drive a real shell on the Mac from the phone*, because `Terminal.app` renders nowhere but the Mac. Every scope call below is decided against that goal, not against feature-parity with VS Code.

### 4.2 Decisions (settled here, do not reopen mid-build)

| # | Decision | Why |
| :-- | :-- | :-- |
| **T-1** | **`portable-pty = "0.9"`** (wezterm). | The only battle-tested option; ships on Apple Silicon in wezterm itself. `tauri-plugin-shell` has **no PTY** — piped stdout means no `$TERM`, no `vim`, no interactive prompts, which fails the ask outright. |
| **T-2** | **`@xterm/xterm@^5.5` + `@xterm/addon-fit@^0.11`.** | The scoped packages are the current publication; the unscoped `xterm` is legacy. `addon-web-links` and `addon-search` deferred. |
| **T-3** | **One shared PTY, not one per device.** | The user wants *the terminal they are already using*, from the phone — not a second, independent shell with a different cwd and history. Matches the roadmap's "the phone is a dumb terminal surface" and the app's whole "Mac is the single source of truth" posture. |
| **T-4** | **The host is the sole resize authority.** | A PTY has exactly one `(cols, rows)`. The companion computes its own fit only to size its rendering box; its xterm instance is resized by an echoed `pty_resize` from the host. Without this, a phone would silently resize the PTY to ~40 columns mid-build and wreck the Mac's output. |
| **T-5** | **No local echo on either screen.** | The PTY is the SSOT for what the terminal shows, exactly like every other bit of state. Both screens render only what the PTY emitted. |
| **T-6** | **DEV / BUILD / REPORT keep launching `Terminal.app`.** | They are *disposable, per-invocation, project-scoped* windows with real polish already invested (double-window avoidance, 124-col auto-snap). The in-app terminal is *one persistent general-purpose* shell. Merging them either drags multi-session/cwd complexity into the MVP or makes build output fight the user's own typing in one PTY. Redirecting them is a **follow-up**, listed in §7. `system.rs:618 run_in_project_terminal` is already the single funnel, so that follow-up stays a one-function change. |
| **T-7** | **No extra confirmation gate for opening the PTY.** | A paired device can already call `run_project_command(local_path, cmd)` — arbitrary command execution on the Mac. A gate on the PTY alone, while that stays open, is security theatre, and it would defeat the entire point (the phone is used precisely when nobody is at the Mac). The pairing token stays the single gate; the honest mitigation is that Remote Control **Off** already kills every companion instantly. This is stated plainly in the CHANGELOG security note rather than quietly shipped. |
| **T-8** | **`pty_spawn` takes `cwd: Option<String>` from the first draft.** | Costs nothing now and is exactly the signature the DEV/BUILD redirect (T-6 follow-up) will need — avoids a breaking signature change one round later. The UI does not expose it yet. |

### 4.3 Never-block-the-UI — the one place the usual pattern is wrong

`CLAUDE.md`'s ABSOLUTE rule says every subprocess-touching `#[tauri::command]` wraps its work in `spawn_blocking`. That holds for `pty_spawn`, `pty_write`, `pty_resize`, `pty_get_scrollback` — all `async fn`, all bounded.

It does **not** hold for the PTY **read loop**. `spawn_blocking`'s pool is sized for bounded one-shot work; parking one of its threads forever in a `reader.read()` loop for the app's whole lifetime starves every other blocking command (`resolve_remote_path`, `check_for_updates`, `get_git_info`, …) of a slot. The read loop gets a **dedicated `std::thread::spawn`**, started once from inside `pty_spawn`'s blocking closure. `portable-pty`'s reader/writer are synchronous `Read`/`Write` trait objects, not `AsyncRead`, so a tokio task would block a worker just as badly.

`AppHandle::emit` is thread-safe and callable from that raw thread — same shape as the existing `sync-log` emit in `src-tauri/src/sync.rs:42`.

### 4.4 Wire path

`FRAME_PTY_INPUT` / `FRAME_PTY_OUTPUT` are **already declared** in `src/constants/protocol.js` and marked "reserved, do NOT implement yet" — flip that comment, add no new constants.

```
[Mac] child process ──► PTY reader thread ──► ring buffer (scrollback, ~256KB cap)
                                │
                                ├─ emit('pty-output') ──► host TerminalView (lowest latency)
                                └─ services/ptyBridge.js ──► bridge.send{t:'pty_output'} ──► phone
[phone] xterm.onData ──► bridge.send{t:'pty_input'} ──► ptyBridge (host) ──► invoke('pty_write')
[Mac]   xterm.onData ─────────────────────────────────────────────────────► invoke('pty_write')
```

Both keystroke sources terminate at the same `pty_write` — one authority, no divergence.

Deliberately **not** routed through `services/mirror.js` (isRef diffing) or `services/intents.js`: raw terminal bytes are a firehose and do not fit a JSON-diffed state model. They are new top-level frames on the same socket, which is precisely what the roadmap reserved room for.

* **Throttle:** the read thread coalesces — flush on ~20 ms elapsed or ~16 KB accumulated, whichever first. A `npm run build` must not turn into one WS message per `read()` syscall.
* **Scrollback replay:** extend the existing `companion-connected` handler (`mirror.js:160-162`) so a joining device also receives the ring buffer as one `pty_output` frame. The relay has no per-connection targeted send, so it goes to everyone — harmless, it is the same shared session.
* **No permessage-deflate** on the relay for now; terminal text is dense enough and LAN/Tailscale bandwidth has never been this app's bottleneck.

### 4.5 Mobile UX

Raw keystrokes, **not** a line-buffered input box. A "type a line, press send" widget cannot Ctrl-C a runaway process, cannot answer an interactive `y/n`, cannot run `vim` — the exact things a terminal exists for. xterm.js's hidden textarea already produces per-character events from the on-screen keyboard, so ordinary typing needs no custom widget.

What a phone keyboard genuinely cannot produce gets **one slim icon row** (Extreme Narrow: one row, small icon buttons, no banner, no labels):

**Esc · Tab · Ctrl (sticky modifier — tap Ctrl, then tap C) · ↑ ↓ ← → · Enter**

Deferred: function keys, Alt/Meta, a configurable key row. None are load-bearing for driving a build
or dev shell from a phone.

### 4.7 Fix round — three defects the first Mac run exposed

The first build reached a Mac and failed in three ways at once. 1.20.0 was never tagged, so these are folded into it rather than minted as a follow-up version (RULE-release A5).

| Reported | Actual cause | Fix |
| :-- | :-- | :-- |
| "Terminal bé, hẹp một góc" | `.pty-terminal` sat in a **row**-direction flex parent (`.terminal-mount-wrap`) with no grow factor, so it sized to its content — an empty div at mount. FitAddon then measured ~0 width and returned its minimum. Compounding it, `doFit()` ran synchronously inside `onMounted`, before the flex chain had resolved a height and before the web font xterm measures cells against had loaded. | `flex: 1; width: 100%; min-width: 0` on the mount; fit deferred a frame, re-run on `document.fonts.ready`, and coalesced per animation frame; fits measuring a container under 40×24px are discarded instead of applied. |
| "ssh rồi exit rồi exit → đứng đơ" | The shell exited, the reader thread ended — and **nothing cleared the session slot**. `pty_spawn` stayed idempotent onto a corpse, `pty_write` wrote into a closed pipe and errored into the console, and the screen never moved again. There was no state, no signal and no control representing "the shell is gone". | The reader retires the slot on EOF (generation-guarded), appends `[process exited]` to the scrollback and emits `pty-exit`; `FRAME_PTY_EXIT` carries it to companions; `pty_get_scrollback` gained `alive`. The frontend turns the tab header red, lights RESTART, and respawns on the next keystroke. |
| "không có nút nào quản lý như VS Code / open in terminal" | Genuinely absent — §4 shipped an MVP with no lifecycle surface at all, which is defensible only until the shell can die, and it can. | CLEAR / RESTART / KILL / OPEN in the **existing** panel header (Extreme Narrow: no new row). New commands `pty_clear`, `pty_restart`, `pty_kill`, `pty_cwd`. Plus **In-App Terminal** in each project's OPEN popup. |

Decisions settled in this round, in the style of §4.2:

| # | Decision | Why |
| :-- | :-- | :-- |
| **T-9** | **The shell is a login shell** (`$SHELL -l`, `TERM=xterm-256color`). | Without it, `.zprofile`/`.bash_profile` never run: no nvm, no rbenv, no `path_helper`. The terminal would have a different `PATH` from every `Terminal.app` window on the machine — the same silent-divergence class as this release's AG-over-SSH bug, and "the terminal you are already using" would be false. |
| **T-10** | **CLEAR wipes the host's ring buffer, not the local screen.** | A local-only clear is a lie: the output returns on the next reconnect and the other screen never clears. The `reset` flag on `pty_output` makes both screens wipe in one beat. |
| **T-11** | **Every spawn carries a generation; a reader only retires the slot it still owns.** | Otherwise a RESTART whose predecessor's EOF arrives late nulls out the brand-new session — a dead terminal with no error anywhere. This is what makes the button safe to double-tap. |
| **T-12** | **A fit measuring an absurd size is discarded, never sent to the PTY.** | A collapsed panel or a mid-transition tab measures near-zero; pushing 2 rows to the real shell permanently re-wraps a running build's output and cannot be undone without a restart. Rejecting is strictly safer than applying — the observer fires again the moment layout settles. |
| **T-13** | **"In-App Terminal" `cd`s by sending keystrokes, not a new command.** | It then behaves exactly like typing it: lands in shell history, respects the shell's own `cd` hooks, needs no host-side surface. Single-quote escaped (`'\''`) so a path cannot break out into command execution. |

## 5. Antigravity remote monitor — two stacked causes

### 5.1 `node` is not on PATH over bare SSH

`src-tauri/src/agent_usage.rs:138`:

```rust
(Interpreter::Node, false) => polling_ssh(host, "node"),
```

Local AG runs `zsh -lc node` (`agent_usage.rs:134-137`) — a **login** shell, so nvm's init in `~/.zshrc`/`~/.bashrc` has run and `node` resolves. `ssh <host> node` runs the remote command in a **non-interactive, non-login** shell: bash does not source `~/.bashrc` there (nvm's line is usually behind an interactive-only guard anyway), zsh sources only `~/.zshenv`. An nvm-installed `node` — the common case — is simply not found. Exit 127.

`Interpreter::Node::preamble()` (`:150`) returns an empty string, while `Interpreter::Sh` gets `CLAUDE_BIN_RESOLVER_PREAMBLE` (`:200-244`). That asymmetry is the whole bug: Claude Code's remote script only needs system-default binaries plus one explicitly-resolved `claude`; AG's remote path has the identical user-installed-binary problem and was never given the same treatment.

It then fails **silently and permanently**: `get_antigravity_usage` (`:625-636`) treats the non-zero exit as a transient soft-miss and swallows it to `Ok(None)`, every poll, forever.

**Fix:** add a `NODE_BIN_RESOLVER_PREAMBLE` following the `CLAUDE_BIN` pattern — static, well-known candidates tested with `[ -x … ]` first (`$HOME/.nvm/versions/node/*/bin/node`, `$HOME/.local/bin/node`, `/opt/homebrew/bin/node`, `/usr/local/bin/node`, `/usr/bin/node`), falling back to `command -v node` only if none match. This is a strict superset of the one-line `bash -lc node` alternative and, per `CLAUDE.md`'s subprocess PATH-resolution rule, is also immune to the cold-start rc-sourcing race that a login shell would still be exposed to.

**Not the cause** (checked and ruled out): the polling loop wiring (`AgentUsageSection.vue:103` creates `agRemote` correctly and it has its own poll timer), the host argument (passed correctly), `set -o pipefail` / the dash pitfall (N/A — the AG probe is a Node script, no shell pipeline), command registration or capabilities (shared with the working CC-remote path), macOS-only credential paths (the probe only does `ps`/`lsof`/`ss` + loopback HTTP, host-appropriate either way), and the `antigravity-usage` npm package (the bundled script explicitly replaces it and is self-contained — there is no architectural blocker; this is a wiring bug).

### 5.2 The remote slot renders **this** Mac's cached numbers

`src/composables/useAgentUsage.js:489-490`, the null branch:

```js
const targetEmail = viewingEmail.value || store.lastActiveEmail
const cached = loadAgAccount(targetEmail)
```

`loadAgAccount` (`:169-178`) matches on **email only** (`k === emailPart || k.startsWith(emailPart + ':')`)
and returns the **first** `Object.entries()` hit. The AG cache map is shared by the local and remote
instances, and both log in with the same Google account — so the remote slot falls back to the local
machine's entry. That is literally the reported *"chỉ hiện của máy tôi"*.

Known and deliberately deferred in `docs/plan/done/1.19.0-final.md`; promoted here because it is what makes
the failure *look like it works*.

**Fix, minimal and additive — no key-format migration, no risk to the multi-account map** (`CLAUDE.md` multi-entity regression guard): record the originating host on each cache entry as it is written, and give `loadAgAccount` a scope argument so a remote instance accepts only an entry whose host matches its own. Legacy entries carry no host and are treated as local-only. A remote host with no reading yet must show an honest empty/stale state, never a number from somewhere else.

**Verification is Mac-side and cannot be done from the dev box.** The distinguishing check for §5.1 is one command on the Mac: `ssh <host> node -v` → "command not found" confirms it. Ship the resolver regardless; it is correct either way.

## 6. Definition of done

## 6a. Where the build deviated from this plan, and why

Recorded rather than silently absorbed, so a later audit can check the diff against the intent.

* **The Node resolver could not reuse `CLAUDE_BIN_RESOLVER_PREAMBLE`'s stdin-prepend mechanism.** That preamble is shell source prepended to a shell script arriving on the same stdin. For the AG probe, stdin carries **pure JavaScript** — prepending shell text hands `node` a syntax error. The resolve-then-`exec`-mid-stream alternative is also unsafe: a shell reading its script from stdin buffers ahead, so JS bytes can already sit in the shell's own read buffer and vanish when `exec` replaces the process image. The resolver is therefore the **ssh remote command itself**, ending in `exec "$NODE_BIN"`; it never reads stdin, so the pipe is untouched when `node` takes over.
* **That resolver is additionally wrapped in `sh -c '…'` and kept to a single line.** `ssh host "<cmd>"` does **not** run `<cmd>` under `sh` — sshd runs it under the remote user's *login* shell. A remote user on `fish` or `csh` would hit a syntax error on `[ -x ]`, `&&`, `$( )` and a multi-line function body alike, exit non-zero, and be swallowed as `Ok(None)` — recreating this very release's silent-forever failure under a different trigger. The bare `node` it replaced was immune because a bare command name parses in any shell; `sh -c '…'` restores that immunity. This is why the script contains no single quote of its own. Verified under real `/usr/bin/dash`: `dash -n` passes and JS piped on stdin survives the `exec` intact. **Not** verified under `csh`/`fish` (neither installed here).
* **`pty_get_scrollback` returns `cols`/`rows` as well as bytes.** Not in §4.6's signature. Without it, a companion opening the Terminal tab mid-session had no way to learn the PTY's real size until the host's own window happened to resize — possibly never. A command return-value change, not a wire change, so §4.4's frozen frame contract is untouched.
* **One new frame, `FRAME_PTY_RESIZE`, was added** beyond the two reserved names — host→companion only, carrying `{cols, rows}`. T-4 needs a resize echo, and overloading `pty_output` (terminal bytes) with size metadata would have been worse than one honestly-named frame.

## 7. Deliberately not in this release

* **A command allowlist on `hostInvoke.js`.** It answers any Tauri command from a paired companion with no filter. PERSIST-1 removes the bug that made this visible, but the surface remains — and it is the same surface the CHANGELOG's 1.19.0 security note already declares by design. Narrowing it is a real decision (which commands? what breaks?), not a cleanup to slip into a bugfix batch.
* **Redirecting DEV / BUILD / REPORT into the in-app terminal** (T-6). Needs multi-session + per-project cwd first. `system.rs:618 run_in_project_terminal` stays the single funnel for it.
* **Moving `useAgentUsage`'s refs into a keyed `usageStore`** (`remote-control.md` §8a's last open R-1 item). Usage numbers are still the one area the mirror does not carry: each screen fetches its own. It is a factory → keyed-singleton conversion touching three instantiation sites — a full workstream of its own, and nothing the user reported depends on it.
* **`projectStore.projectIcons` is filled only at boot**, so a project added mid-session has no icon on the phone until reload. Known, cosmetic.
* **`logStore.projectLogs` has no line cap** (`remote-control.md` risk R-3), and `logStore.consoleRef` holds a DOM node that the mirror drops with a warning every session. Both cosmetic today.
