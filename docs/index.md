- [docs/research/terminal-vietnamese-ime-root-cause-4.md](research/terminal-vietnamese-ime-root-cause-4.md) - Not the head of the chain anymore - read `-5.md` below first. The whole chain's mechanism was backwards: WebKit sets `keyCode 229` only when a real input method consumed the event and un-sets it for a modeless engine like OpenKey, while Chromium sets it with no IME at all for any multi-character insertion - so VS Code works *because* Chromium mis-tags the carrier into xterm's value-based 229 path. The actual defect is one line of xterm 5.5.0 (`_keyPress` takes one UTF-16 unit of a multi-character `event.key`), and the decided fix is a ~90-line text drain on xterm's own textarea replacing ~750 lines of app-owned key encoding - public API only, no vendoring, no xterm 6.x upgrade. **§7 point 1 (the "narrow" keypress veto) and its exclusivity table's first row are superseded by `-5.md`** - everything else here stands
- [docs/research/terminal-vietnamese-ime-root-cause-5.md](research/terminal-vietnamese-ime-root-cause-5.md) - **Head of this chain.** The jul31 double-space blocker `-4.md` did not predict: `_keyPress` cancels without `force` and xterm's own `cancel()` is a no-op unless `cancelEvents` is on, so space (fails `Keyboard.ts`'s `keyCode >= 48` test) and uppercase A-Z (the caps-lock HACK) both reached `_keyPress` uncancelled while the browser also mutated the textarea - xterm sent the character and the drain sent it again. Fix broadens the keypress veto from "multi-character carrier only" to "every keypress", one branch removed rather than a guard added. Confirmed on real hardware 2026-07-31: predicted `TEST` -> `TTEÉTT` before the fix, clean after, on both the Mac and a remote Chrome/Android session; the Android/Gboard defect is untouched and stays a separate open item
- [docs/research/terminal-gboard-double-insert.md](research/terminal-gboard-double-insert.md) - Code-level root-cause trace (no Android hardware in this environment, so unconfirmed) for the Android/Gboard doubling left open by `terminal-input-jul31.md` §2.2: the drain's "read all, then empty" textarea model has no way to honor a `deleteContentBackward` the IME fires against text it already forwarded and erased, so the delete silently drops and only the correction's `insertText` lands, appended after the base run it was meant to replace (`báo cáo` -> `baoáo caoáo`).
