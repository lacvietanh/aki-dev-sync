- [docs/research/terminal-vietnamese-ime-root-cause-4.md](research/terminal-vietnamese-ime-root-cause-4.md) - **Head of this chain - read this one, not the three above, before touching the IME path.** The whole chain's mechanism was backwards: WebKit sets `keyCode 229` only when a real input method consumed the event and un-sets it for a modeless engine like OpenKey, while Chromium sets it with no IME at all for any multi-character insertion - so VS Code works *because* Chromium mis-tags the carrier into xterm's value-based 229 path. The actual defect is one line of xterm 5.5.0 (`_keyPress` takes one UTF-16 unit of a multi-character `event.key`), and the decided fix is a ~90-line text drain on xterm's own textarea replacing ~750 lines of app-owned key encoding - public API only, no vendoring, no xterm 6.x upgrade
