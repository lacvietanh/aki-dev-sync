# Settings and state — four owners, four files

> updated 2026-09-28 · v1.31.0

Decision record and field-by-field reasoning: `docs/research/akidevsync-project-config-scope-2.md`.
Execution plan and checklist: `docs/plan/settings-and-state-layout.md` (see its § Amendments for the 1.32.1 `remote_path` correction below). This doc is the current-state summary the two of them point at — read them for *why*, this for *what's true now*.

## The four owners

| # | File | Scope | Sole-owner module | What lives there |
|---|---|---|---|---|
| 1 | `<local_path>/.akidevsync/notes.json` | travels with the project | `project_notes.rs` | per-project tasks/notes (unchanged since 1.22.0) |
| 2 | `<local_path>/.akidevsync/project.json` | travels with the project | `project_config.rs` | `name`, `production_url`, `pull_excludes`, `push_excludes`, `commands.{dev,build}` |
| 3 | `~/.aki/devsync/projects.json` | this machine only | `projects.rs` | registry: `id`, `local_path`, `order`, `disabled`, `dry_run`, `delete_on_*`, `remote_host`, `remote_path` (fixed across every host, 1.32.1), `targets.<host>.hooks` |
| 4 | `~/.aki/devsync/state/<project_id>/<host>/{baseline.json,last_sync.json}` | this machine only, per (project, host) | `sync_state.rs` | sync baseline (+ the `remote_path` it was recorded against) and the most recent sync outcome |

A file's owning module is the only Rust code that reads or writes it directly. Every other module reaches that data through the owner's public functions (`read_project_config`, `read_baseline`, `write_last_sync`, …) — never by re-deriving the path itself. This is what keeps the four-owner split from decaying back into one god-file: a second module that learns to spell `state/<id>/<host>/baseline.json` on its own is the first step of `sync_state.rs` losing sole ownership.

## Why a project fact and a machine fact never share a file

`project.json` (#2) holds what stays true regardless of which Mac opens the repo — "a file already in the repo wins" over the registry, the same precedent `notes.json` set in 1.22.0. `projects.json` (#3) holds what is true only for *this* machine's copy: which local path it lives at, which host it's currently pointed at, whether background polling is on, and `remote_path` — a fact about the *project*, not the host:
a project has exactly one remote directory regardless of which host serves it, so it stays a plain top-level field and a Remote Host switch never touches it (1.32.1 correction; briefly lived in `targets.<host>` during 1.32.0, see `docs/plan/settings-and-state-layout.md` § Amendments). `hooks` genuinely ARE per-**host** — a real hook embeds that host's own shell paths — so they still sit in `targets` (#3's own field), restored on a Remote Host switch (`resolveHostSwitch`, `useProjectConfig.js`) while `remote_path` stays fixed throughout that same switch. `deploy` is a top-level field that names its own host and is never touched by that switch (`docs/research/sync-host-safety.md`).

`state/` (#4) is neither — a baseline is a fact about what was last made common between exactly this project and exactly this host, and mixing hosts here would report false conflicts. Renaming an SSH alias therefore forfeits that host's baseline (the directory name is the alias itself, `validate_remote_host`), and a baseline whose recorded `remote_path` no longer matches the target's current one counts as **no baseline at all** — the ancestor is someone else's tree — enforced by one shared filter (`sync::baseline_for_target`) on both the post-sync write and the status-check read, so the two paths can never drift out of agreement with each other again (the write path was missing this filter until this release's S1 fix).

## Read-through and write-through, end to end

- **`project.json` fields** (`name`, `production_url`, `pull_excludes`, `push_excludes`, `dev_cmd_override`, `build_cmd_override`): `useProjectConfig.js::applyConfigToProject` copies a successful read onto the matching registry object — at boot/Refresh (`hydrateProjectConfig`) and on config-dialog open (`refreshProjectConfig`) — only when the read status is `ok`, so a Missing/Unavailable/Corrupt read never blanks an existing in-memory value. The save funnel (`saveProjectsList`, via the pure `buildProjectSavePayload`) resets these six fields to empty/`null` in the **payload only**, and does so **only for a project whose current config status is `ok`** — a project.json missing/unavailable/corrupt keeps sending its registry copy unchanged, since that copy is still the only one that exists: a legacy registry copy is removed only once its new home actually holds it. `#[serde(default, skip_serializing_if = ...)]` on `SyncProject` then drops the stripped fields from the persisted registry JSON for good.
  PUSH/PULL and the background status check refuse to run at all while a project's status is not `ok` (`useSync.js::startSync`, `useSyncStatus.js::checkProjectSyncStatus`) — a UX-level gate only, since a cached `ok` status can briefly outlive the fresh object it described (a titlebar Refresh replaces `projects.value` before the batch re-read finishes). The floor that actually matters lives in Rust:
  `run_sync`, `check_sync_status` and `get_sync_delete_preview` (`sync.rs`, via `project_config::require_ok_excludes`) re-read `.akidevsync/project.json` from disk inside their own `spawn_blocking` closure at the moment they build rsync args, and refuse outright when that read is not `ok` — the JS-passed `SyncProject`'s excludes are never trusted as the source. `loadData` also resets every cached status to `unknown` before it replaces `projects.value`, so the JS gate itself cannot be fooled by a stale `ok` either.
- **`targets.<remote_host>.hooks`**: `hydrateRemoteFromTargets` restores it onto the top-level `hooks` field on every load, before anything else reads it. `SyncProject`'s top-level `hooks` field is stripped from the save payload once a target holds it (`buildProjectSavePayload`).
- **`remote_path`** (1.32.1): always the top-level field, never restored from a target — `hydrateRemoteFromTargets` only falls back to a target's (deprecated) copy when the top-level value is genuinely empty, a self-heal for a registry the boot migration hasn't touched yet. `validate_project_paths` requires it non-empty on every save, same destructive-sync safety floor as before.
- **`last_sync_*`** (`action`, `time`, `status`, `host`): `useSync.js::startSync` calls `write_last_sync` directly into `state/<id>/<host>/last_sync.json` on both the success and error paths, instead of setting it on the registry object for `save_projects` to carry. `hydrateLastSyncFromState` (called from `loadData`, which both boot and titlebar Refresh share) reads `read_last_sync_all` and sets the four fields in memory — newest `last_sync.json` across a project's hosts wins, answering "which host did I last sync with," and `ProjectTable.vue`'s last-action cell consumes it as-is. The delete-preview auto-approval in `useSync.js`, however, needs the **active** host's own sync time, not the newest across every host — a more recent sync to a different host must never suppress a delete confirmation for this one — so it calls the single-pair `read_last_sync_for_host` command instead of reading the hydrated newest-wins field. The save funnel also resets the four hydrated fields to `null` in the payload, same mechanism as the six `project.json` fields — the registry file never re-accumulates them even if a stale hydrate left them `Some` in memory.

## Migration — one shot, in `setup()`, before the logger opens

`sync_state::migrate_settings_and_state_on_boot` runs directly inside `lib.rs`'s `.setup()` closure, immediately after `app_paths::migrate_legacy_app_data` and before `logger::init` — not from JS on every load/Refresh. This matters because `sync::baseline_dir()`'s fallback path (used whenever the `APP_DATA_DIR` `OnceLock` is unset, which is always true this early) needs a deterministic resolution: it was previously falling back to a pre-1.7.1 legacy directory "that should not happen in practice," which running the migration from JS after other IPC commands had primed `APP_DATA_DIR` would have hidden. Order:

1. Load `projects.json` directly (`projects::load_projects_blocking`) — no frontend exists yet at this point in startup.
2. Per project: `remote_host` + `hooks` → `targets.<remote_host>`, only if that entry is absent (an existing target entry — e.g. from a sync that already ran this launch — always wins).
3. Per project (1.32.1 fix): if the top-level `remote_path` is empty, lift it from `targets.<remote_host>`'s (deprecated) copy, else from the first target that has one — then clear `remote_path` out of every target so a pre-1.32.1 value can never resurface. A project already carrying a real top-level value is left untouched.
4. Per project: the legacy flat `baselines/<id>.json` → `state/<id>/<host>/baseline.json`, stamped with the current `remote_path`, using `last_sync_host` if present else `remote_host` as the best-guess pairing — but **only if no per-host baseline already exists** for that pair; a fresher `state/` baseline (written earlier this same launch) is never overwritten by a stale legacy file. The legacy file is removed either way once consulted.
5. Per project: `last_sync_action/time/status` → `state/<id>/<host>/last_sync.json`, then cleared (`None`) on the project object.
6. Save only if something actually changed (`changed` flag) — a no-op second run writes nothing, verified byte-identical across repeated runs.

## Deprecated fields, and when they go

| Field(s) | Struct | Deprecated since | Current contract | Removal |
|---|---|---|---|---|
| `name`, `production_url`, `pull_excludes`, `push_excludes`, `dev_cmd_override`, `build_cmd_override` | `SyncProject` | 1.32.0 | `#[serde(default, skip_serializing_if = ...)]` — loads from a legacy file, never persists once stripped | not yet scheduled; kept for one release's worth of upgrade safety |
| `hooks` (top-level) | `SyncProject` | 1.32.0 | `#[serde(default, skip_serializing_if = is_default_hooks)]` — restored from `targets.<remote_host>` on load | not yet scheduled |
| `remote_path` (on `Target`) | `Target` | 1.32.1 | `#[serde(default, skip_serializing_if = "String::is_empty")]` — migration-only, lifted onto `SyncProject.remote_path` and cleared; never written by app code again | not yet scheduled |
| `last_sync_action`, `last_sync_time`, `last_sync_host`, `last_sync_status` | `SyncProject` | 1.32.0 | `#[serde(default, skip_serializing_if = "Option::is_none")]` — one-time migration read, then always sent as `null` by the save funnel | not yet scheduled |
| `tasks`, `notes` | `SyncProject` | 1.22.0 (typed `ProjectTask` struct removed 1.32.0) | `Option<serde_json::Value>`, opaque — survives load → save until `useProjectNotes.js::migrateLegacyProjectNotes` moves it into `.akidevsync/notes.json` | not yet scheduled |

None of these fields have a scheduled removal version yet — removing a `#[serde(default)]` field is safe at any time (an old file simply stops carrying data nobody reads), but doing so before every real-world project has passed through the migration at least once would drop data for a project on a volume that stayed unmounted since before the migrating release. Track removal against `docs/plan/`, not this doc — this doc states the current shape only ([[RULE-docs]] A2).
