# Terminal stack — architecture

> updated 2026-10-20 · v1.33.1

How the in-app terminal's frontend is layered, and how terminal v2's SCOPES (tab groups) sit on top of it without touching Rust. User-facing behaviour: `docs/feat/in-app-terminal.md`.

## The layering

Four layers, each with a single job:

- **Shared session state** — `src/store/terminalTabsStore.js`. Holds `terminalTabs` (the list), mutated only through `action()`-wrapped functions so a companion's gesture (tap a tab's ✕ on the phone) executes on the host, whose state change then mirrors back to every screen. `services/mirror.js` auto-discovers every `isRef` export under `src/store/` (SSOT-1); the two navigation refs — `activeTerminalTabId` and `activeTerminalScope` — opt out via `PER_SCREEN_KEYS`, because which tab/group a screen is looking at is that screen's own navigation, not session data.
- **Per-screen glue** — `src/composables/useTerminalTabs.js`. Liveness (`tabAlive`, re-exported from `usePtyTerminal`'s module-level tracker), `activatedTabs` (which tabs this screen has ever mounted), `lastTabByScope` (which tab each scope was last looking at, VSCode-group style), and the companion's pending-activation claim (scope-keyed, with a short TTL so a claim the host refuses cannot strand and later steal focus). None of this is mirrored — the file says why per ref, since each is either screen-local navigation or something a companion's own PTY event stream already reconstructs.
- **Panel chrome** — `DockStack.vue` (shared base) + the specializations `dock/LogStack.vue` and `dock/TerminalStack.vue`, each owning its own per-screen collapse ref. This is **composition with a shared base and slot-injected content**, not class inheritance — `DockStack` renders the header/body/peek chrome, emits `update:collapsed`, and owns that stack's resize handle; each specialization fills its own `#title` / `#actions` / `#peek` slots and owns its own script. Both collapse via the same chevron (COLLAPSE/EXPAND) and both pass `bodyPersist`, so a collapse keeps their content mounted rather than destroying it.
- **Dock geometry** — `useDockLayout.js`, per-screen. See "The dock is the sum of its stacks" below.
- **PTY surface** — `usePtyTerminal.js` + `TerminalView.vue`. One `usePtyTerminal(term, tabId)` instance per mounted `TerminalView`, filtering Tauri events and companion frames by `tab_id`.

## Scope as the aggregate root

A **scope** is a tab group. Its key is `scopeOf(tab) = tab.projectId || GLOBAL_SCOPE` — grouping is derived entirely from a field the tab record already carried (`projectId`); nothing new went on the wire for the tab list itself. A scope owns its tabs; a tab's membership in one is nothing more than that field.

Invariants:

- **No scope has a floor, global included (2026-07-28).** Every group — a project's, or the global one — may go to zero tabs; it simply stops existing until its terminal button is clicked again, at which point `openScopeTerminal` (via `openProjectTerminal` / `openGlobalTerminal`) creates a fresh tab. Global used to be pinned to a permanent one-tab minimum (seeded at boot by `initTerminalTabs`, enforced on close by `terminalTabsStore.js`'s `closeTerminalTab`); that was removed because it was the actual mechanism behind a real bug, not just an inconsistency — a dev-server HMR reload re-runs the boot seed, and a `pty_list_tabs()` call racing the backend into reporting an empty list (even with a shell already live) would seed another tab on top of it, piling up phantom "Shell" chips across repeated reloads. Every scope is now symmetric: opened on demand, closeable to zero, no special case.
- `pty::SCROLLBACK_CAP` also binds `web_server.rs`'s `COMPANION_QUEUE_LIMIT_BYTES` via **INVARIANT R** (`base64_len(SCROLLBACK_CAP) + ~128 ≤ COMPANION_QUEUE_LIMIT_BYTES / 4`), asserted by a Rust unit test rather than left to a comment: the per-tab cap is the load-bearing constant, not a tab count. Raising `SCROLLBACK_CAP` or lowering `COMPANION_QUEUE_LIMIT_BYTES` re-breaks a joining phone's scrollback replay; the test exists to catch exactly that.
- Closing a scope's last tab falls back to global scope; the stale-id reconcile watcher in `useTerminalTabs.js` covers the companion boot / cross-screen-close cases.
- **Scope-empty ⇒ fall back to global — the SAME rule for every scope, global included.** Closing any scope's last tab forgets that scope's remembered tab (`forgetScopeTab`, multi-entity guard: scoped to the ONE scope, never clears the whole map), resets `activeTerminalScope` to `GLOBAL_SCOPE`, and activates the global group's remembered (or most recent) tab if it has one. Global closing its own last tab is simply the identity case of this rule: `activeTerminalScope` is already `GLOBAL_SCOPE`, and if it has no remaining tab either, the group just renders empty — the same "click the terminal button again to open a fresh one" state a project group has always had. The stale-id reconcile watcher in `useTerminalTabs.js` performs the same fallback defensively for the companion boot / cross-screen-close cases the direct `closeTab` path does not cover, and is itself a no-op when no scope anywhere has a tab left.

### Companion add is fire-and-forget — the repeat-tap guard (1.22.0)

Opening a tab from a companion never gets the tab back: `addTerminalTab`'s `action()` stub (`src/services/action.js`) sends the intent and returns `undefined` immediately, so the caller only learns a tab exists once the host's mirror echoes it back. `useTerminalTabs.js`'s `openScopeTerminal` bridges that gap with a scope-keyed "queue-of-one" claim (`pendingActivateScope`, TTL'd) that the tab-list watcher resolves once the mirror arrives — full mechanism in the doc comment at its definition.

Before 1.22.0 that round trip had a second cost: the reuse and capacity pre-checks both read the still-stale mirrored list while it was in flight, so a repeat tap on the same scope's TERM button before the tab arrived passed both checks again and opened a second tab — nothing told the tapper the first one was already on its way. `openScopeTerminal` now no-ops a repeat call for a scope with a live claim already outstanding, so only the first tap sends an add.

**Any new "open/duplicate a terminal" entry point must call `openScopeTerminal`, not `addTerminalTab` directly** — the guard lives in the caller, so bypassing `openScopeTerminal` bypasses it too.

**The one deliberate exception: DEV/BUILD (`docs/plan/done/dev-build-in-app-launch.md`, #7).** `ProjectTable.vue`'s DEV/BUILD buttons — a third entry point alongside the TERM cell and the header icon — call `useTerminalTabs.js`'s `openRunCommand`, not `openScopeTerminal`. `openScopeTerminal`'s reuse check is scope-only ("does this scope already have a tab?"); DEV/BUILD needs a scope **and** `runKind` match ("does this scope already have a *dev* tab?" — a project may have an ordinary shell and a running dev server open at the same time, and pressing BUILD must never touch DEV's tab). `openRunCommand` re-implements the create-or-focus shape against that finer key, tags the new tab `runKind: 'dev' | 'build'`, and stashes the literal command in a `pendingCmd` field that `usePtyTerminal.js` sends once, on the tab's `alive` transitioning to `true` — new spawn or respawn alike, same watcher.

**Known gap the guard does not close:** two browser tabs open on the same phone are two separate page loads, so `pendingActivateScope` (module-scope, per page) is not shared between them. Same per-page-state root cause as the `invoke_result` cross-talk that per-connection addressing fixed in 1.21.1 (`docs/feat/remote-control.md`) — but unfixed here, since closing it needs the guard to live host-side, inside `addTerminalTab`'s own body, not in the composable.

## The capability pattern

`usePtyTerminal` publishes capability flags — `ownsPtySize` (does this screen decide the shared PTY's cols/rows RIGHT NOW — a getter, not a fixed role, since resize authority is an explicit, revocable claim as of `docs/plan/done/wish-terminal-manual-resize-authority.md`), `showReclaimPill` (host-only: does a companion currently hold that claim?), and `showKeyRow` (does this surface need the synthetic Esc/Tab/arrow/Ctrl row, including the companion-only "Fit to my screen" claim button?) — instead of exposing a role flag; `TerminalView.vue` asks the capability, never `isHost`. Scope adds no new capability: grouping is pure frontend navigation, invisible to the PTY layer entirely.

**Capability × preference (1.25).** `useTerminalChrome.js` layers a second, orthogonal axis on top of the same pattern: `chromeVisible[control] = capability(control, thisScreen) && preference[control]`. `hostAvailable`/`companionAvailable` on each entry in its `CONTROLS` list are the capability half — the same role-availability question `showKeyRow` etc. already answer — and a per-device `localStorage` preference is layered over it, never the reverse; preference can never turn on a control the screen has no capability for. `TerminalStack.vue` and `TerminalView.vue` read the resulting `chromeVisible` map only, same discipline as the rest of this section: neither gains an `isHost` import. Feature-level behaviour: `docs/feat/in-app-terminal.md` § Terminal chrome visibility.

## Keyboard input: xterm owns keys, the app owns text

`TerminalView.vue`'s PTY surface splits input into two disjoint claims, enforced structurally rather than by classifying key type:

- **Keys** — arrows, modifiers, F-keys, bracketed paste, DECCKM, Alt-as-meta — stay entirely inside xterm.js's own `_keyDown` / `evaluateKeyboardEvent` pipeline, untouched. xterm already gets this right; an earlier app-owned overlay textarea that re-implemented it regressed six ways (arrows ignoring application cursor mode, F5 emitting PageUp, paste losing its bracketing, Option+word-motion sending nothing).
- **Text** — everything that lands as a rendered character — has exactly **one** path to the PTY: `useTerminalTextDrain.js`'s capture-phase `input` listener on xterm's own textarea. `customKeyEventHandler` vetoes **every** `keypress` (`return false` unconditionally, not scoped to a subset of keys), which skips xterm's own `_keyPress` **without** calling `preventDefault`; the browser still inserts the character into the textarea, and the drain reads, clears, and sends it once.

The exclusivity this buys is a DOM specification guarantee — `preventDefault` on a key event suppresses the following textarea mutation and its `input` event — not an internal xterm behaviour the app has to keep matching: any key xterm force-cancels at `_keyDown` never produces a keypress at all, so the drain never sees it; any keypress that does fire is always vetoed, so it is always the drain, never xterm, that sends the resulting text. An earlier, narrower veto (only xterm's multi-character IME carrier signature) left two key classes — space and uppercase A-Z — reaching `_keyPress` without a forced cancel, so xterm sent them AND the drain sent them again; full mechanism and file:line evidence in `docs/research/terminal-vietnamese-ime-root-cause-5.md`, decision record in `-4.md` §7. `useTerminalInput.js` (the app-owned overlay) and `useWkImeGuard.js` (a capture-phase guard on xterm's internal handlers) were the two prior approaches; both are deleted.

**The one key the app takes back: `⌘C` (2026-08-20).** xterm's own copy route is a native `copy` DOM event on `.xterm`, fed from `selectionService.selectionText` — and the only place xterm ever puts a selection where a browser could copy it from is the Linux primary-selection path (`onLinuxMouseSelection`). On macOS the hidden textarea stays empty and the painted highlight is not a DOM selection, so WKWebView raises no `copy` event and `⌘C` had never copied anything, on any target, since the terminal shipped. `useTerminalCopy.js` claims the key in the capture phase on `term.element` and writes `term.getSelection()` through `utils/clipboard.js`'s `copyText()` — the app-wide clipboard path, not a second implementation. This does not weaken the split above: xterm never asked for `⌘C` (`_keyDown` yields no `key` for `⌘`+letter on macOS and returns without `cancel()`), so nothing is being taken from it, and with no selection the handler returns before touching the event, leaving today's behaviour exactly as it was.

The same composable owns a second, related defect: xterm's `CoreMouseService` fires `onProtocolChange` on **every** assignment to `activeProtocol` — including re-arming the protocol already active — and `bindMouse`'s handler answers it with `selectionService.disable()`, which clears the selection outright. A TUI that re-emits its own mouse mode while the user is selecting therefore erases the selection; the composable swallows the redundant assignment on that one instance, feature-detected so an xterm upgrade degrades to the old behaviour instead of throwing. Because it is not yet proven that `claude` re-arms in place rather than disarming first, the selection is **also** stashed on every non-empty selection change, so `⌘C` copies correctly even when the highlight is gone by the time the key is pressed. The mouse itself stays with xterm: the app does not intercept mousedown. OSC 52 (`term.parser.registerOscHandler(52)`) is a third clipboard ingress for remote tools and does not take the mouse. Counters are readable on demand at `window.__akiTermCopy.status()`. Root cause and evidence: `docs/research/terminal-copy-selection-root-cause.md`.

## PTY backend contract

One PTY per `tab_id`; `pty_spawn` is idempotent; liveness travels on `pty_output` / `pty_exit`, never on the mirror (there is deliberately no `alive` field on the `terminalTabs` record — mirroring one would be a second, competing source of truth for a fact the PTY events already carry with lower latency); `pty_close_tab` requires its `tab_id` argument (a defaultable "close" is exactly the accidental-blast-radius shape the multi-entity regression guard forbids); each live tab costs roughly three raw OS threads and up to 128 KiB of scrollback ring buffer; the app-exit hook kills every tab's process group.

**Terminal v2 required zero Rust changes.** The backend was already tab-keyed and knows nothing about "projects" or "groups" — scope is a pure frontend grouping over `projectId`, a field the tab list already carried before this work. If any part of this feature had needed a Rust change, that would have meant the frontend-only premise was wrong.

**Backend storage.** `src-tauri/src/pty.rs` keys every piece of session state by a `TabId` (`u32`): `sessions`, `inputs`, `scrollbacks` are each a `HashMap<TabId, _>` instead of a singleton, and `min_accepted` (the generation-fencing floor) is a **per-tab** map — a single global floor would let retiring one tab's generation fence off a still-live generation in another tab. Every command takes an `Option<u32> tab_id` defaulting to tab 0, the backward-compatibility seam for a companion frontend that never sends `tab_id`. The one exception is `pty_close_tab`, whose `tab_id` is **required** — a defaultable "close" is exactly the accidental-blast-radius shape the multi-entity regression guard forbids. `pty_list_tabs()` returns `{id, alive}` per tab so a reloaded frontend can re-adopt shells the backend kept running.

## Wire format

`pty_output` / `pty_input` / `pty_resize` / `pty_exit` all carry `tab_id` (default 0). This matters because the relay (`web_server.rs`) coalesces `pty_output` frames under congestion by tag alone, content-blind — without `tab_id` on every frame, a coalesce could silently land tab A's bytes in tab B's xterm. `pty_output` also carries an optional `reset` flag meaning "replace everything, do not append", set by RESTART and scrollback replay.

**One new frame type, deliberately (1.24, `docs/plan/done/wish-terminal-manual-resize-authority.md`):** `pty_resize_request` (companion → host, `{tab_id, cols, rows}`) — a companion's "Fit to my screen" tap, honored unconditionally on arrival. A narrow, stated exception to the "no new frame types" discipline this section used to claim as absolute: it is the fifth member of this same firehose-adjacent PTY frame family, not a new per-feature category — see that doc for why `resizeOwner` itself (who currently holds the claim) still rides the ordinary `terminalTabs` mirror instead of a frame.

**Per-companion addressing (1.21.1).** A scrollback replay (a `pty_output` with `reset: true`) and an `invoke_result` are addressed to the one companion they are for, via an optional `to` field the relay routes on and an optional `from` field the relay stamps on the way in — see `docs/feat/remote-control.md` for the wire-level detail. Before this, both were broadcast: a second phone joining wiped and rebuilt the screen of a phone already mid-command, and two phones with an overlapping `invoke` call in flight could resolve each other's replies. Live `pty_output`, `pty_exit`, `pty_resize`, `delta` and `init` all still broadcast, since every screen genuinely needs the same bytes.

**Resync.** `pushScrollback()` became `pushScrollbacks(to)` in `src/services/ptyBridge.js`: on a fresh companion connect or a scheduled resync, it calls `pty_list_tabs()` then replays scrollback for tabs past tab 0, so the same congestion that forces a resync does not leave later tabs silently un-replayed on the device that just reconnected. To stop the reconnect burst from growing with tab count, full scrollback is **bounded to `REPLAY_SCROLLBACK_TAB_LIMIT` (4) tabs** — chosen active-tab → pinned → list-order fill by the pure `selectHydratedTabs` helper in `src/services/replayHydration.js` (unit-tested in `scripts/tests/replay-hydration.test.mjs`); every other tab still gets an authoritative empty `reset` carrying size/liveness/existence. The companion-join path passes the joining device's id so only that phone receives the replay; the host's own congestion-recovery path still broadcasts, because the dropped frame was a broadcast every companion missed and there is no single device to address it to. Rationale + as-built: `docs/plan/done/companion-replay-bound.md`.

## How the bytes move

```
[Mac] shell ──► PTY reader thread ──► ring buffer (scrollback)
                       │
                       ├─ emit('pty-output') ──────────► the Mac's own terminal (lowest latency)
                       └─ services/ptyBridge.js ──────► pty_output frame ──► phone
[phone] keystroke ──► pty_input frame ──► ptyBridge (Mac) ──┐
[Mac]   keystroke ──────────────────────────────────────────┴──► pty_write  (one authority)
```

Terminal bytes ride five top-level frames on the existing socket (`pty_input`, `pty_output`, `pty_resize`, `pty_resize_request`, `pty_exit`), never the state mirror or the intent registry — raw output is a firehose and does not fit a JSON-diffed state model. The first two names were reserved in `src/constants/protocol.js` a release ahead of time for exactly this. Bytes are base64 end-to-end and never treated as a Rust `String`; the frontend decodes to a `Uint8Array` and hands it to xterm.js, whose own stateful UTF-8 decoder reassembles a multi-byte character split across two PTY reads. Output is coalesced (about every 20ms, or 16KB, whichever comes first) so a chatty build does not become one network message per `read()`. `pty_exit` is a separate signal rather than something parsed out of the `[process exited]` text: driving state by pattern-matching our own cosmetic output would break the moment the wording changed.

## Never-block-the-UI, and the one place the usual rule inverts

`pty_spawn` / `pty_resize` / `pty_get_scrollback` are all `async fn` wrapping their work in `spawn_blocking`, per the ABSOLUTE rule in `CLAUDE.md`. `pty_write` is the deliberate exception: synchronous, because it waits on nothing and being async would break input order (§ Input: one queue, a synchronous `pty_write`). `pty_rename_tab` / `pty_set_tab_pinned` are plain `fn` too: one in-memory map insert.

The **read loop is a dedicated `std::thread`, and must stay one.** `spawn_blocking`'s pool is sized for bounded one-shot work; parking one of its threads forever in a `read()` loop for the app's whole lifetime starves every other blocking command (remote path resolution, update check, git info) of a slot. A tokio task would be just as wrong — `portable-pty`'s reader is a synchronous `Read`, so it would block a worker identically. This is the one spot in the app where "just wrap it in `spawn_blocking`" is the bug rather than the fix.

### Restart cannot orphan or clobber a session

Every spawn takes a generation number. A reader thread only retires the session slot if the session sitting in it is still the one it was reading. Without that, a shell killed by restart whose EOF arrives a moment late would null out the brand-new session that replaced it — leaving a terminal that is dead with no error anywhere and no way to tell why.

The same generation floor fences a **closed** tab: closing raises its floor to `u64::MAX` so late bytes from the dying reader cannot recreate the scrollback entry and resurrect the tab in `pty_list_tabs`. The frontend allocates new ids as `max(id)+1`, so closing the highest tab hands its id to the next one; every real spawn therefore sets its tab's floor to its own generation (`admit_generation`), which admits the new session and keeps every older one rejected. Without that step a reused id is silent — the shell runs, its output is dropped (1.31.0 regression, fixed after it).

### Creating a shell never holds the session map

`openpty` + `spawn_command` (a `fork` on macOS, because `portable-pty` installs a `pre_exec` hook) run under `spawn_gate`, not under `sessions`, so a slow spawn cannot stall resize, cwd, list or kill on the tabs that already exist. The gate also makes a second spawn for the same tab wait and then no-op on the live shell, which callers that write into the shell right after `pty_spawn` returns depend on.

A kill cannot reach a shell that is still being created, so `spawn_inflight` carries a "retired" flag: `kill_session` (close, kill, restart) sets it for that tab and `kill_all_sessions` (app exit) for whichever is in flight, both under `sessions`; the commit reads it under the same lock and reaps the new shell instead of installing it. The flag is deliberately not the close fence above: `u64::MAX` also marks a closed id that is about to be reused, so reading it as "closed mid-spawn" would kill the reused tab's fresh shell. Design record and rejected alternatives: `docs/plan/done/terminal-pty-spawn-lock-isolation.md`.

### Killing the shell means killing its process group

`portable_pty`'s `Child::kill()` signals only the direct child — the login shell. Everything the user started *inside* that shell (`ssh host`, a dev server) is a separate process in the shell's process group, and a signal aimed at the shell alone need not reach it; a surviving `ssh` keeps the remote `sshd` session and whatever runs under it (`agy`, `claude`, 300–500 MB each) alive. `kill_process_group` therefore sends SIGHUP to the whole group first (`killpg`, the same signal closing a real terminal window sends) and escalates to SIGKILL only for what survives a 300 ms grace (12 × 25 ms, polled with signal 0 so the common case returns in ~25 ms, which matters because app exit pays it once per live tab). `portable-pty` puts the child in its own session on unix (`setsid` + `TIOCSCTTY`), so the child's pid is its process-group id and one `killpg` reaches every descendant. `terminate_child` runs the group kill, then `child.kill()` as the backstop for a child that is not a group leader, then `wait`; it blocks up to the grace, so it never runs under a session lock. What `killpg` buys is narrower than it looks: `killing_the_shell_takes_processes_started_inside_it_with_it` also passes with a plain `kill` on the shell (verified by mutation), because the kernel SIGHUPs the foreground group when a session leader with a controlling terminal dies. `killpg` covers what the kernel does not: a process that left the foreground group, and a teardown where the ctty is not revoked.

The bigger half of the fix is *when* teardown runs: `pty::shutdown` is wired to `RunEvent::Exit` in `lib.rs`. Every other path into a kill is a user gesture (KILL, RESTART, close), so before that hook existed, quitting the app ran no teardown whatsoever. `kill_all_sessions`, reachable only from `shutdown`, is the module's only whole-map operation: quitting is the one "close everything" the owner asks for.

**How much `killpg` itself buys, stated honestly.** The unit test `killing_the_shell_takes_processes_started_inside_it_with_it` still passes with `killpg` swapped for a plain `kill` on the shell — verified by mutation, not assumed. When a session leader holding a controlling terminal dies, the kernel SIGHUPs the foreground process group on its own, so an ordinary foreground child dies either way. `killpg` covers what the kernel does not: a process that has left the foreground group, and any teardown path where the ctty is not revoked.

The orphaned `ssh` clients investigated in 1.20.0 were not caused by this code: they matched, to the second, hand-typed `ssh` commands in `Terminal.app` tabs later closed (`~/.zsh_history`), and the app binary installed then contained no PTY symbols at all.

## PTY backend internals (`pty.rs`)

### Lock order

`sessions` → `inputs`, `scrollbacks` → `min_accepted`, `sessions` → `spawn_inflight`, `OutBuf` → `min_accepted`. `min_accepted`, `spawn_inflight` and `tab_meta` are leaf locks; no path holds both `OutBuf` and `scrollbacks`. A slow operation (process-group kill, spawn) never runs under `sessions`: `kill_session` removes the session under the lock and kills after releasing it, `kill_all_sessions` snapshots ids first, `pty_list_tabs` takes `tab_meta` per id.

### Output: coalescing with a deadline

Each live session has one `OutBuf` (accumulator + last-flush clock + `done`), shared by its reader thread and a flusher thread. Bytes flush at 20 ms (`FLUSH_INTERVAL`) or 16 KB (`FLUSH_BYTES`), whichever comes first. The deadline needs its own thread: when the test lived only in the read loop, the next flush could only come from the next `read()` returning, so a keystroke echo arriving within 20 ms of the previous flush stayed invisible on an idle shell until unrelated output arrived. `flusher_loop` sleeps on a condvar while nothing is pending (an idle shell costs no wakeups), waits out only the rest of the current window in a predicate loop (a single `wait_timeout` would be cut short by the next chunk's `notify_one` and defeat coalescing), and exits when its reader sets `done`. `flush_locked` runs with the `OutBuf` mutex held and drains the whole accumulator per call, so payload order is byte order with nothing duplicated or dropped. The reader emits its own tail before the exit notice, so the shell's last line always precedes it. The emit goes to the Mac's `TerminalView` directly and to `services/ptyBridge.js`, which relays it as a `pty_output` frame.

### Input: one queue, a synchronous `pty_write`

`pty_write` used to lock the session and write; two keystrokes are two independent commands, so the mutex kept the writes apart but did not order them (`ls` could arrive as `sl`, certain under a paste or companion replay). Now each session has an mpsc queue drained by one writer thread (`writer_loop` → `drain_input_queue`, flushed per chunk because a chunk is a keystroke or a paste). `pty_write` is synchronous on purpose: it only decodes base64 and sends on the channel, so it cannot block, and a sync command runs inline on the IPC dispatch thread in the order the webview posted the calls; an async one could be polled on two workers and race to the enqueue. The cost: a write error cannot be returned to the caller. It surfaces as the writer retiring its channel (the next keystroke returns "no PTY session") and the reader emitting `pty-exit`. The writer retires only its own tab's channel and only at its own generation, so it never removes the channel a `pty_restart` already installed. Killing a session drops the sender, which ends the writer and makes a late `pty_write` fail instead of queueing for a dead shell.

### Generations fence bytes, not only the slot

A killed shell's reader lives up to one `FLUSH_INTERVAL` longer and can still flush bytes; on a restart those landed above the fresh prompt, in a scrollback just cleared for the new shell. `min_accepted` is a per-tab floor: `kill_session` raises it past the killed generation (`retire_generation`, kill-only, since a shell that hits EOF has no late writer to fence), and both the scrollback append and the emit drop bytes from a generation below it. The append tests the floor under the `scrollbacks` lock, the same lock `retire_generation` publishes under, so an append either finishes before the retirement (and is cleared by the restart that follows) or sees the new floor. The emit path reads the floor through the leaf lock only, because it already holds `OutBuf`. The floor is per tab because generations are global: one global floor would let retiring tab 10's generation silence tab 11's older, still-live one. Text that is not session output (`append_scrollback(.., None)`) always lands.

### Liveness rides the output channel

`PtyOutputPayload.alive` is `Some(x)` only on the payloads where liveness changes (spawn, kill, EOF) and is absent from the JSON otherwise; the frontend's `typeof alive === 'boolean'` test is the whole protocol. The hot byte path never takes `sessions` to stamp it. Before it existed, a screen that saw the shell exit stayed convinced it was dead, and its next keystroke tore down the shell another screen had just restarted. `pty_restart`'s three emits are ordered: `reset` while the slot is empty (so it cannot wipe the new prompt), then the spawn, then `emit_alive` (so it reports the new session). One combined payload is wrong in one direction or the other. `pty_spawn` broadcasts liveness on its no-op path too, because the other screen may still believe the shell is dead. The exit notice carries `alive: false` as well as the separate `pty-exit`, since the two reach a companion on different frames. `reset` wipes one tab on every screen at once; `pty_clear` uses it to empty the host's ring buffer, which the shell's own `clear` leaves full for the next phone that reconnects. `tab_id` is mandatory on every payload: every `TerminalView` filters on it.

### Tab metadata survives a reload

`TabMeta` (`project_id`, `title`, `pinned`) outlives the shell and a webview reload, and is forgotten only by `drop_tab_state` on close; `adoptTabs` (`terminalTabsStore.js`) rebuilds scope, title and pin from `pty_list_tabs`, which returns the union of tabs with a session and tabs with a scrollback (an exited tab still has one a phone may read). `upsert_tab_meta` patches: `None` leaves a field alone, so an older companion calling `pty_spawn` without ownership cannot erase it. `project_id` is set at the first spawn and never moved.

### The spawned shell

`$SHELL -l` (fallback `/bin/zsh`): a login shell sources `.zprofile`, so nvm, rbenv and `path_helper` give the same PATH as any `Terminal.app` window. The child's PATH is seeded with the well-known macOS install dirs before rc sourcing starts (R-1, `docs/plan/done/dev-build-in-app-launch.md`), so a DEV/BUILD command written right after spawn does not race `.zprofile` into `exit=127`; an nvm-managed node is not covered. `CLAUDE_CODE_CHILD_SESSION` is stripped from the inherited env so `claude` in a tab still saves transcripts. `cwd` applies only on a tab's first real spawn; the initial size is 80x24 until the host's first `pty_resize`. The host is the only caller of `pty_resize`; a companion is resized by the echoed frame, a frontend-side discipline the command cannot enforce. `pty_get_scrollback` returns the size and liveness with the buffer, so a screen joining mid-session applies the right size and state without waiting for the next host resize. `pty_cwd` reads the shell's current directory through `lsof` (macOS has no `/proc`); on failure the caller falls back to `$HOME`.

The end-of-session notice names only a control that is on screen (it once said "click RESTART" after that button was gone), and it is written into the scrollback so a screen that opens the tab later still sees why the terminal is idle.

## Mount semantics

`TerminalStack.vue`'s mount loop (`v-for="t in tabs"`, the FULL unfiltered list) iterates every tab regardless of scope, on purpose: `v-if="activatedTabs.has(t.id)"` mounts a `TerminalView` lazily on first activation and keeps it mounted afterward, and only `v-show="t.id === activeTabId"` changes when the visible tab or the visible scope changes. Filtering the mount loop by scope would unmount and re-spawn xterms on every group switch — the tab strip (`TerminalTabStrip.vue`) is what is scope-filtered (`scopedTabs`), not the mount loop.

A stack **collapse** for `TerminalStack.vue` preserves state via `DockStack.vue`'s `bodyPersist` prop: the default slot is wrapped in `.dock-stack-body` and kept mounted instead of destroyed with `v-if`, so a collapse→expand round-trip disposes and re-spawns nothing, and scroll position and a full-screen program's painted screen survive it. `LogStack.vue` does not pass `bodyPersist`, unmounting the 2000-line console output when collapsed so only the 44px header + peek slot are rendered in the DOM.

In **Right-dock mode** (window width ≥ 900px via `useRightDockLayout.js`), `TerminalStack` moves into a dedicated right column taking all remaining width (`flex: 1`), while `LogStack` sits at the bottom of the main view column (`dashboard-left`). In right-dock mode, collapse and maximize controls in `TerminalStack` are hidden as the terminal column is dedicated. Below 900px, `TerminalStack` and `LogStack` return to the bottom dock (`dashboard-bottom`) with full independent collapse and maximize controls.

The re-fit on expand is not a new code path: `TerminalStack.vue` passes `active` as `t.id === activeTabId && !collapsed`, and `TerminalView.vue`'s existing `watch(() => props.active)` re-fits and refocuses on the false→true edge (the refocus goes through `nextTick`: at the default `pre` flush it lands on an element `v-show` has not revealed yet and is silently dropped, which is what left `TerminalStack.vue`'s shortcut gate refusing every terminal shortcut after one tab switch). While hidden the container measures 0 and `doFit()`'s `width < 40 || height < 24` floor discards the measurement, so nothing resizes the live PTY.

`TerminalStack.vue` also collapses **itself** once `tabs.value.length` (the full, unfiltered list) reaches 0 — every tab in every scope closed, by any close path (a chip's ✕, ⌘W on the last one, etc.) — a `watch` sets `collapsed.value = true` rather than a per-close-path special case, since it is state-driven, not path-driven. The collapse/expand transition itself is a `main.css` rule on `.dock-stack`: `flex-grow`/`flex-basis` (numeric, so a `transition` can ease it), not the `flex: none` shorthand (whose implicit `auto` basis a transition can't interpolate toward) — shared with `LogStack.vue`, so both stacks ease shut/open instead of snapping.

## The dock is the sum of its stacks

**Each stack owns its own length; the dock's height is their sum** (`useDockLayout.js`, per-screen — a composable rather than a `src/store/` module, so `mirror.js` never discovers it and a phone's drag cannot resize the Mac's window layout). Collapsing or expanding one stack therefore changes only the dock total, and the sibling's length is arithmetically untouched.

It used to be the inverse — one stored dock height that two `flex: 1 1 0` stacks divided — and that is what coupled two panels the UI presents as independent: the total did not depend on which stacks were expanded, so the space a collapsing stack freed went to its sibling's `flex-grow` instead of back to the app. Full defect table and the six gestures it broke: `docs/plan/done/dock-stack-independent-height.md`.

- **Resize** is per stack: each *expanded* stack renders its own 3px `.dock-splitter` at its top (`DockStack.vue`, which is why the component has two root nodes — the handle's negative margin and its 11px hit area must sit outside `.dock-stack { overflow: hidden }`). A collapsed stack renders none: its length is a fixed header row, so the gesture would be inert.
- **Nothing grows.** Every stack's `flex` is written inline from `dockStackFlex(key)` with `flex-grow: 0`. A single `flex-grow: 1` anywhere restores the old coupling.
- **`height: auto` is deliberately avoided** even though it computes the same sum: a length cannot be transitioned to or from `auto`, so an auto-sized dock would snap on every collapse. `dockHeightCss` is a `calc()` string over the same `--dock-header-h` / `--dock-peek-h` tokens the stylesheet uses, which is also what keeps the geometry and the CSS from disagreeing about what a collapsed stack measures.
- **MAXIMIZE is the one mode that suspends the sum**: the dock takes `calc(100vh - titlebar)` and the expanded stacks share it with `flex: 1 1 0`. It is still not persisted, and collapsing everything still leaves it.
- **A drag suppresses both transitions** (`.is-dragging` on the dock covers `.dock-stack` too). That is not only about lag: firing no transition events is what keeps `dockAnimating` false, and therefore what keeps `TerminalView`'s live per-frame fit during a resize.

The cost is retention: every mounted xterm keeps its 5000-line scrollback while the panel is closed.

## Right dock — the console box moves to a column above 1220px

Above a 1220px window width (`useRightDockLayout.js`'s `MAIN_VIEW_MAX_WIDTH` 900 + `RIGHT_DOCK_MIN_WIDTH` 320), the whole console box — the terminal stack with the log stack beneath it, both unchanged internally — relocates from the bottom of the window into a right-hand column, and the project table caps at 900px so the column has room. This is a second, independent axis, not a replacement for the height-summed model above: `useDockLayout.js` still owns each stack's own vertical split inside the box in both modes, and `DockStack.vue`, `TerminalStack.vue` and `LogStack.vue` are untouched by the dock relocation — only the box's own axis and length source change.

`rightDockActive` (`useRightDockLayout.js`) is the single ref every consumer reads to decide placement; nothing else recomputes the trigger. `App.vue` toggles `.is-right-dock` on the dashboard's main wrapper from it, and `AppConsole.vue` reads the same ref to choose which length source drives the box: `dockHeightCss` (the existing height-summed value) in narrow mode, or `rightColumnWidthCss` in right-dock mode. A vertical splitter on the column's left edge (`AppConsole.vue`, `rightColumnWidthPct`, persisted to `localStorage` under `aki-right-dock-width-pct`, clamped 20–60%) drags the column's width; MAXIMIZE reuses the same `dockMaximized` ref the height axis already owns, so the existing button keeps working unchanged once the column is width-docked. Being a composable rather than a `src/store/` module, `rightDockActive` and the column width are per-screen and never mirrored to a companion.

Design research: `docs/research/terminal-stack-right-dock.md`.

## External `Terminal.app` count — derived, never remembered

The `TERM` cell's bottom (slate) badge is **not** part of the PTY stack at all: it counts *external* `Terminal.app` sessions attributed to a project, and it is a **live scan, not a tally**. That is the whole architectural point — the app can observe itself opening a window but never observes the user closing one, so any remembered counter can only grow and eventually lies.

One producer, host-only (seam P): `composables/useExternalTerminals.js` calls the `list_terminal_sessions` command (`src-tauri/src/system.rs`) every **5 s**, plus once ~800 ms after the app opens a Terminal window. Each scan is three short local subprocesses on the blocking pool — `pgrep -x Terminal`, one `ps -axo pid=,ppid=,tty=,etime=,command=` walked into Terminal's descendant set, one batched `lsof -a -d cwd -p <pids> -F pn` (capped at 200 pids). `list_terminal_sessions` is zero-arg and returns one row per session — `{pid, ppid, tty, cwd, owner}`; attribution is a frontend decision now, not something the scan itself bucket by path: `src/utils/terminalOwnership.js`'s `attributeTerminalSessions(sessions, projects)` is the single decision point that turns that inventory into `byProjectId` counts and a `globalCount`, applying §3's tagged-then-adopted-then-unowned priority (below) — no Vue, no `invoke` inside it.

The result replaces `projectStore.externalTermCounts` and `externalTermGlobalCount` wholesale each tick, both derived from the same scan. That is not a multi-entity "clear": every key is rewritten from the same single scan, and no function resets part of it. Being store refs, the mirror carries the snapshot to every companion for free — the phone must never poll, since Terminal's process table exists only on the Mac.

### The detail modal shares the scan, not just the idea (1.22.0)

`describe_terminal_sessions` answers "which sessions, and what is running in them" and is the same pipeline: both commands go through `scan_terminal_tree`, which owns the three subprocesses and hands back `(ppid_of, cwd_of, row_of)`. It kept its `paths` argument through S1 — the plan's original acceptance criteria called for dropping it, but the sessions modal's "in X's folder" label needs each session's `local_path` match, which only `paths` supplies, so code reality overrode the doc's stated end-state here. The same subtree-root test underlies both commands, so the modal's row count and the badge's number are the same fact computed once — a second, parallel definition of "one session" is precisely how the two would come to disagree.

The split is in *cadence*, not in logic: the badge polls every 5 s and needs only a count; the modal is on-demand and returns a command line per process, which must never ride the poll. Both are host-only and neither is in `COMPANION_ALLOWED_COMMANDS`; the badge reaches a phone through the mirrored `externalTermCounts` snapshot, and the modal's button simply does not render there (`externalTerminalsSupported`, published as a capability rather than an `isHost` read at the call site, in keeping with the capability pattern above).

### Spawn-origin ownership — the scan still owns existence, a registry now owns origin

`docs/plan/done/terminal-ownership-model.md` §3's reconciliation rule is now **fully built (S1–S6)**: **the scan is still the sole authority on which sessions exist** — nothing below changes that. Since S3, a second, separate authority tracks *who launched* an already-counted session; since S1/S2 (2026-08-16) that authority also drives the badge counts, not just the modal's label.

`TerminalOwnership` (`src-tauri/src/system.rs`, `by_tty: Mutex<HashMap<String, OwnedSession>>`, Tauri-managed state) records `(tty → owner)` at the moment `open_local_terminal` or `open_remote_subprocess("terminal")` reads a tty back from the AppleScript that opened the window (`tag_terminal_launch`). `reconcile_terminal_owners` runs at the top of every scan: it pins the owning pid on first sight and drops a registry entry the instant its tty (or pinned pid) no longer appears in the live Terminal tree — one entry at a time, never a bulk clear (the multi-entity guard, CLAUDE.md). A launch whose tty could not be read back stays untagged; that session is simply not in the registry, not an error.

**What this changes: both the modal's per-row label and the badge counts.** `describe_terminal_sessions` and `list_terminal_sessions` both report each session's `owner`. `ExternalTerminalsModal.vue` reads "launched from X" for a tagged session (registry hit, cwd not consulted at all) versus "in X's folder" for one merely adopted by matching `local_path` (today's pre-existing cwd rule, unchanged) versus a bare directory name for neither. `src/utils/terminalOwnership.js`'s `attributeTerminalSessions` applies the same tagged-then-adopted-then-unowned priority to produce the badge counts (`byProjectId`, `globalCount`), so the badge and the modal can no longer disagree about which project a session belongs to. An SSH terminal opened from a project's OPEN popup is tagged and now counts on that project's badge even though its cwd is the local `$HOME`; a session the app did not open still falls back to the directory-matching rule.

### Opening a `Terminal.app` window — one window, its tty read back

`open_terminal_with_command` (`system.rs`) is the single funnel for every external Terminal window the app opens (local, SSH, AkiDevRule install).
- **No double window on cold start.** A Terminal launched from scratch creates its own default window; `do script` would open a second one. The script reuses `window 1` instead, waiting for it by polling (up to ~2 s, every 100 ms), never a flat `delay`, which a heavy `.zshrc` (nvm, conda) outruns. With Terminal already running, `do script` opens a new window as usual.
- **The tty is read back at this one boundary.** The script returns the new session's `/dev/ttysNNN`; an empty result is logged here (`terminal-owner`, "tty readback empty") so a Mac log tells a broken AppleScript contract from a session with no tty. What an empty tty means (the session stays untagged and cwd adoption applies) is decided only in `tag_terminal_launch`. Reading it makes the call `.output()`, so every caller is `async` + `spawn_blocking`. Not covered by a test: that `tty of t` is populated in the same script that opened the window.
- **The window is snapped by a separate, fire-and-forget `osascript`** (`snap_frontmost_terminal_window`): 124 columns, top-right of the main display, full available height. Columns are set first, at the original position where the window can grow, then one move+resize goes through System Events' `AXPosition`/`AXSize`: Terminal's own `bounds` was observed to keep the old Y on a jump to another display. It needs Accessibility permission for the process running `osascript`; macOS prompts on first use.
